# 暖色設計 token 與元件樣式

## 這個功能幫我做什麼

一整套已經調好、已經在真實系統上用過的**視覺基底**：配色、字級、間距、圓角、陰影、語意色、狀態徽章。

新專案不用重新想「主色要用什麼」「警示色要多深」——複製 `tokens.css` 進去，直接開始寫版面。

## 這份檔案已經跨專案用過了

`tokens.css` 的檔頭寫的是「**Warm Design System — Colors & Typography（暖意版）**」，
但它出現在領據單據系統裡。

**同一份設計 token 已經被兩個技術完全不同的系統共用**（個案管理系統 是 Python/Flask + Jinja，物資系統是 React + Vite）。
這證明它真的是可移植的——**因為它只是 CSS 變數，不綁任何框架。**

## 內容結構

```
:root {
  ── 中性（warm cream / ink）
     --bg-app #fbf6ef      暖米底
     --bg-app-admin        管理端用更深一階，一眼分辨身分
     --bg-surface / -2 / -3
     --fg-1 ~ --fg-faint   文字五階
     --border / -strong / -dashed

  ── sky 群組（資訊 / 連結）     重新指派為「暖暮藍」
  ── 語意：success / warn / danger  各 4–9 階
  ── 分級色 g1~g4
  ── 字級、間距、圓角、陰影
}
```

`app.css` 是建立在這些 token 之上的**元件樣式**：按鈕、卡片、表格、表單、狀態徽章、篩選 chip。

## 三個設計決定

### 1. 保留原 token 名稱，只換數值

檔頭寫得很清楚：

> 本檔保留 暖色設計系統所有原 token 名稱，僅重新指派為暖意版本的數值，
> 讓既有的 utility class / 文件 / preview 不需改名即可對齊。

**改版時換數值不換名稱。** 這樣整個專案的樣式檔一行都不用動，換個 `tokens.css` 就變了皮膚。
`--sky-*` 這組名字明明已經是暖暮藍了還叫 sky，就是為了這個——**名稱的穩定比名稱的準確重要**。

### 2. 為什麼是暖色 + 大字

> 主視覺：暖米底 + 赭土紅 + 柔和圓角 + 大字。
> 字級主要落在 16–20px；KPI 38px。

這不是美學偏好，是使用情境：**相容老花、視力不佳的長者與長時間值班的社工。**
從冷灰實用轉為暖米，是為了降低長時間盯螢幕的疲勞。

移植時如果你的使用者是年輕人、需要高資訊密度，這個決定要重新做——**但要知道你在推翻什麼。**

### 3. 管理端與使用端用不同底色

`--bg-app` 給一般使用者、`--bg-app-admin` 深一階給管理端。
**一眼就知道自己現在是什麼身分。** 這比在角落放一行文字有效得多。

## 移植點

`tokens.css` — **整份複製，然後只改品牌色那幾行。**

| 要改的 | 說明 |
|---|---|
| `--bg-app` / `--bg-app-admin` | 底色。想換冷色系就從這裡開始 |
| 品牌主色（赭土紅） | 換成你的主色，但**要重新檢查它在暖米底上的對比度** |
| `--sky-*` 群組 | 如果不需要「連結色」這個角色可以留著不用 |
| 字級 | 使用者不是長者的話可以縮小一到兩階 |

`app.css` — **選擇性移植**。它綁著特定的 class 命名。建議只抄你需要的元件（按鈕、狀態徽章、表格），不要整份搬。

**改配色時的守則**：語意色（成功綠 / 警示黃 / 危險紅）**不要跟品牌色混用**。品牌色是識別，語意色是資訊——混在一起使用者就分不出「這是強調」還是「這是警告」。

## 已知限制

- **只有亮色。** 沒有暗色模式的 token。要加的話是在 `@media (prefers-color-scheme: dark)` 裡重新指派同一組變數名。
- `app.css` 的 class 命名跟原專案的 HTML 結構耦合，不是一套通用 utility framework。
- 沒有元件預覽頁。原始的 暖色設計系統有 19 頁 HTML 規格預覽（色彩、字級、元件），**那個之後值得單獨收錄**——它才是真正能「看到」的部分。
