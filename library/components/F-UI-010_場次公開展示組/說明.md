# 場次公開展示組

## 這個功能幫我做什麼

**把「網站上的活動資訊」從手寫改成資料庫直出，開一場就自己出現、結束就自己歸檔。**

原本首頁與活動頁上有 400 多行手寫的活動卡，每辦一場就要有人去改 HTML，辦完還要記得撤掉。改完之後：

- **即將舉行**——後台開一場就出現，過期自動消失。名額滿了自動變「已額滿」按鈕不能按；還沒決定要不要上架的場次可以顯示「即將開放，敬請期待」但不給報名。
- **活動軌跡**——辦過的場次永久留著，依民國年摺疊（「115 年（5 場）」），讓新來的人看見這個社群累積了多少。
- **主題還沒公布時顯示「神秘驚喜！」**——不是留白，也不是有人記得去打那四個字。
- **舊的線上會議連結會自己消失**——不靠人記得刪。

## 技術線

```
sessions（後台維護）
  status: open / full / closed / done / cancelled
  topic, guest（可留空）
        ↓  create view，只挑安全欄位
sessions_public   ← 沒有 meet_url、沒有 calendar_event_id
        ↓  再加一層欄位白名單
   getUpcomingSessions()   status in (open, full[, closed]) 且 ends_at >= now
   getPastSessions()       status = done，最新在前
        ↓
 UpcomingSessions.tsx        SessionHistory.tsx
   四種卡片狀態                依民國年 <details> 摺疊
```

### 為什麼是「狀態欄位」而不是「日期比大小」

| | 前台用日期判斷 | 存成 status 欄位（本作法） |
|---|---|---|
| 「已結束」怎麼來 | 每次載入比對現在時間 | 資料庫裡就是 `done` |
| 辦到一半取消的場次 | 分不出來，時間到了就變已結束 | `cancelled`，永遠不進公開軌跡 |
| 建好但還不想公開 | 沒辦法表達 | `closed`，顯示「即將開放」但不給報名 |
| 測試資料 | 會混進正式畫面 | 標 `cancelled` 就隔離了 |
| 代價 | — | 需要有人（或一段 SQL）把過期的改成 `done`，見下方順序防呆 |

關鍵差別在**「已結束」和「不該出現」是兩件事**。只用日期比大小的話，這兩件事會被合成同一件，取消的場次和測試資料就會混進歷史紀錄。

## 核心手法

### 一、未公布 ＝ 欄位留空，前台自己補話

主題與客座來賓做成**真欄位**，而不是從標題文字去猜有沒有公布：

```sql
alter table public.sessions
  add column if not exists topic text,
  add column if not exists guest text;

comment on column public.sessions.topic is '本場主題。留空時前台顯示「神秘驚喜！」。';
```

```tsx
// UpcomingSessions.tsx:76
const mystery = (value?: string) =>
  value ? <>{value}</> : <span className="font-black text-highlight">神秘驚喜！</span>;
```

這樣「公布主題」變成一個**真的動作**：後台把欄位填上去，前台就換掉那四個字。相對地，如果靠標題含不含關鍵字來判斷，那句佔位語就變成一個沒人管得住的猜測，改個標題就會誤判。

同一個手法可以換成任何佔位語——「講者待定」「地點另行公告」——重點是**留空是一種合法狀態，而不是漏填**。

### 二、敏感欄位靠 view 結構性下架

歷史場次卡裡本來有 4 個寫死的線上會議連結。新版不是「把連結刪掉」，是**讓那個欄位根本到不了前台**：

```sql
create or replace view public.sessions_public
with (security_barrier) as
  select s.id, s.project_id, s.title, s.starts_at, s.ends_at,
         s.capacity, s.booked_count, s.status,
         s.registration_deadline, s.slot_options, s.quota_group,
         s.topic, s.guest          -- 沒有 meet_url、沒有 calendar_event_id
  from public.sessions s
  where exists (select 1 from public.projects p
                where p.id = s.project_id and p.is_public);
grant select on public.sessions_public to anon, authenticated;
```

前台再加第二層白名單（`SAFE_COLUMNS` 明列要哪些欄位，而不是 `select *`）。**兩層都是白名單**：資料庫新增一個敏感欄位時，它不會因為誰忘了改前端就外流。

前台查詢還留了一條退路：view 不存在（migration 沒跑）時退回查本表，讓開發環境不會整頁掛掉。

### 三、四種卡片狀態由兩個值決定

```tsx
// UpcomingSessions.tsx:100
const remaining = Math.max(0, s.capacity - s.bookedCount);
const isFull = s.status === 'full' || remaining === 0;
const notYetOpen = s.status === 'closed';
```

`isFull` **同時看狀態與數字**，兩者任一成立就算滿。這是刻意的重複判斷：後台改名額但忘了改狀態時，前台仍然擋得住。按鈕與名額文字都由這兩個布林值推導，不會出現「顯示剩 0 名但按鈕還能按」。

### 四、載入中、失敗、真的沒有——三種空狀態要分開

```tsx
if (sessions === null) return <>場次載入中…</>;          // 還沒回來
...
{failed ? '場次資訊暫時無法載入，歡迎加入官方 LINE…'      // 失敗
        : '新場次公布後會直接出現在這裡…'}                 // 真的沒有
```

用 `null` 表示「還沒回來」、空陣列表示「回來了但沒有」，中間隔一個 `failed` 旗標。壞掉的時候給的是替代管道，不是一片空白讓人以為活動停辦了。`SessionHistory` 則相反——查不到就整段不顯示（`return null`），因為一個還沒辦過活動的網站不需要一個空的「活動軌跡」區塊。

### 五、過期歸位的順序不能對調

活動軌跡上線前要先把過期場次的狀態歸位，這段 SQL 的兩個步驟**順序寫錯就會出事**：

```sql
-- 步驟 1：測試場次除役（必須先做）
update public.sessions s set status = 'cancelled', admin_note = ... || '除役原因…'
where ... s.title like '%測試%' and s.status <> 'cancelled';

-- 步驟 2：過期場次歸位為 done（cancelled 不受影響）
update public.sessions set status = 'done'
where status in ('open', 'full') and ends_at < now();
```

順序相反的話，那筆「已過期且額滿」的測試場次會先被掃成 `done`，然後大方出現在公開的活動軌跡裡。另外注意它**不刪任何資料**——測試場次改標 `cancelled` 並在 `admin_note` 寫下原因，保留稽核。詳見知能 `K-RESIL-002`。

### 查詢層（原專案寫法，供對照）

```ts
const SAFE_COLUMNS = 'id, project_id, title, starts_at, ends_at, capacity, booked_count, status, topic, guest, registration_deadline, slot_options';

// 即將舉行：open/full（可選加 closed），且尚未結束
.from('sessions_public').select(SAFE_COLUMNS)
  .eq('project_id', projectId)
  .in('status', includeUnpublished ? ['open','full','closed'] : ['open','full'])
  .gte('ends_at', new Date().toISOString())
  .order('starts_at', { ascending: true });

// 活動軌跡：只取 done，最新在前
.from('sessions_public').select(SAFE_COLUMNS)
  .eq('project_id', projectId).eq('status', 'done')
  .order('starts_at', { ascending: false });
```

`includeUnpublished`（顯示「即將開放」）**只給服務頁用，報名頁不要開**——否則使用者會看到還沒上架的場次出現在可選清單裡。

## 已知限制

- **每個元件各自查一次資料庫。** 同一頁同時放「即將舉行」與「活動軌跡」會發兩組請求（各含一次 `getProjectBySlug`）。頁數少時無所謂，要省的話把 project 查詢提到外層傳進來。
- **時間格式用瀏覽器時區。** `new Date(iso).getHours()` 走使用者本機時區，跨時區的使用者會看到不同的時間。原專案的服務對象都在台灣所以沒處理。
- **`status='done'` 需要有人去改。** 附的 SQL 是一次性歸位，不是排程。長期跑的話要加定期任務或改成查詢時判斷，否則過期場次會卡在 `open` 一直顯示在「即將舉行」。
- **活動軌跡沒有分頁。** 一次全部載入並依年摺疊，場次累積到幾百場時要加分頁或只載最近三年。
- **`title like '%測試%'` 是脆弱的辨識法。** 靠命名慣例，取名叫「壓力測試專場」的真實活動會被誤標 `cancelled`。原專案接受這個風險是因為場次量少且執行前逐筆看過——照抄前請先確認自己的資料也是這個規模。
- **`admin_note` 是用字串接的**（`coalesce(admin_note || E'\n', '')`）。多跑幾次不同的除役 SQL 會愈接愈長，沒有結構化。
