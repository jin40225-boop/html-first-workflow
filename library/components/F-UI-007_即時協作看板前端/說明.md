# 即時協作看板前端

## 這個功能幫我做什麼

活動或課程進行中，**主持人和參與者看同一塊板子**：

- 參與者用手機掃碼加入，填暱稱與心情
- 主持人看得到每個人的狀態、誰舉手、誰需要協助
- 即時聊天、表情反應、計時器、階段指示

**配 `F-INT-002 Google Apps Script 試算表後端` 才是完整一套**——那支是後端（Google 試算表當資料庫），這支是前端。
兩條合起來就是一個**零主機成本的即時協作系統**。

## 技術線

```
JoinPage.tsx    參與者：掃碼進來 → 填暱稱/心情/意向 → 進場
BoardPage.tsx   主持人：看全場狀態、推進階段、發指示、控計時器
contracts.ts    前後端共用的請求/回應型別
      ↓  每 REFRESH_SECONDS 輪詢一次
Apps Script /exec  →  Google 試算表
```

## 四個核心設計

### 1. 輪詢，不是 WebSocket

Google Apps Script 沒有 WebSocket。所以走輪詢，間隔在後端定成常數（預設 5 秒）。

**對這個場景夠用**：課程活動的狀態變化以秒計不以毫秒計，5 秒延遲沒有人會發現。
而換來的是**整套系統不用租任何主機**。

**判準**：即時性需求是「秒」還是「毫秒」？是秒 → 輪詢就好，省下整個即時架構。

### 2. 兩個角色兩個頁面，不是同一頁切換

`JoinPage` 給參與者（手機、簡單、只有幾個欄位）
`BoardPage` 給主持人（桌機、資訊密集、45 KB）

**不做成同一頁依角色顯示不同區塊**——兩者的使用情境、螢幕、心智負荷完全不同，
硬要共用只會兩邊都難用。

### 3. 狀態欄位設計得很細

參與者身上有這些欄位：

```
nickname, mood, intent, join_mode, energy, status_text,
hand_raised, cued, is_visible, is_locked, last_seen_at
```

**`mood` / `energy` / `intent` 這些不是裝飾**——在帶團體的情境裡，
「誰現在狀態不好」「誰想發言」是主持人最需要的資訊，比「誰在線上」重要得多。

`cued`（被點到）與 `hand_raised`（舉手）分開，是因為那是兩個方向的動作。

### 4. 前後端共用契約檔

`contracts.ts` 兩邊各一份（`src/lib/` 與 `backend/`）。
Apps Script 沒有型別，但把契約寫成 TypeScript 放旁邊，前端就有提示、改欄位時知道哪裡會壞。

## 移植點

| 位置 | 要改的 |
|---|---|
| `BoardPage.tsx`（45 KB） | **這是最專案專屬的部分**，整個版面要重寫 |
| `JoinPage.tsx` | 參與者填的欄位 |
| `contracts.ts` | 跟後端一起改 |
| 輪詢間隔 | 在後端的 `REFRESH_SECONDS`（見 `F-INT-002`） |

**可以整段照抄的**：兩角色兩頁面的切法、輪詢的資料流結構、共用契約檔的做法、參與者狀態欄位的設計思路。

## 相依套件

React + Vite。API 端點走環境變數 `VITE_APPS_SCRIPT_API_URL`。

## 已知限制

- **輪詢有延遲**（預設 5 秒）且會持續消耗 Apps Script 配額。人多或活動長會撞上限。
- `BoardPage.tsx` 45 KB 是單一檔案，該拆成元件。
- 沒有離線處理。手機網路斷掉時的行為未定義。
- 安全只靠共用的 `ADMIN_TOKEN`——**不適合放任何敏感內容**（見 `F-INT-002` 的限制）。
