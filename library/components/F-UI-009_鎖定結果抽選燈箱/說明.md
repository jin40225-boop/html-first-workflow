# 鎖定結果的抽選燈箱

## 這個功能幫我做什麼

從指定名單抽出一至三人，提供兩種呈現：

- **爬格子**：以 SVG 畫出直線、橫槓與中選路徑。
- **隨機選人**：以卡片翻動呈現已鎖定人選。

動畫完整放在燈箱，不讓操作介面長期占用貼文版面。使用者可以重播同一結果；要產生新結果，必須再次通過伺服器端編輯碼。

## 技術線

```
POST /draws
  ├─ crypto.getRandomValues：無偏差亂數洗牌
  ├─ 建立 winners、rungs、serial
  └─ 將完整結果存回資料庫
              ↓
DrawLightbox.tsx
  ├─ SVG 路徑 + getTotalLength
  ├─ Web Animations API
  └─ 重播只重啟動畫，不重新抽選
```

## 核心設計

### 一、結果生成與動畫播放完全分開

後端先產生並保存結果，前端動畫只是揭示。重播時不呼叫重新抽選 API，所以重新整理、換裝置或多次播放都不會改變中選人。

### 二、重新抽選是另一個明確動作

`start` 遇到既有結果會直接回傳原結果；只有 `redraw` 且編輯碼驗證通過，才會建立新序號與新結果。
這讓「看動畫」與「推翻結果」不可能因按錯同一顆按鈕而混在一起。

### 三、兼顧減少動態效果偏好

偵測 `prefers-reduced-motion: reduce` 時，把動畫時間縮到近乎立即，保留結果與操作，不強迫使用者觀看移動效果。

## 移植點

| 位置 | 要改的 |
|---|---|
| `route.ts` | 資料表、授權函式與編輯碼驗證 |
| `DrawLightbox.tsx` | 色彩、文案、燈箱尺寸與結果卡樣式 |
| `DrawResult` 型別 | 新專案的序號、稽核欄位與抽選上限 |
| 呼叫端 | 將開始、重播、再來一次分成三個不同操作 |

## 相依套件

無額外動畫套件。使用瀏覽器原生 Web Animations API、SVG 與 Web Crypto。

## 驗證重點

- 第一次開始後，伺服器必須回傳並保存 `serial`、中選者與動畫所需資料；同一筆再次開始只能拿到相同序號與結果。
- 「重播」只能操作既有 DOM／SVG 動畫，不得送出新的抽選請求；網路面板應看不到新增結果的 POST。
- 「重新抽選」必須走獨立端點並重新驗證編輯碼，成功後才出現新序號。驗證失敗時，舊結果仍須可讀且不可被清空。
- 前後端要成對移植：只拿燈箱會失去結果鎖定，只拿 API 則缺少可理解的揭示與減少動態效果處理。
- 關閉再重新開啟燈箱後仍應讀到同一筆已保存結果；畫面狀態不能成為結果的唯一保存位置，資料庫才是正式結果的真相來源。

## 已知限制

- 燈箱元件預期接收已由後端保存的結果；不要把亂數生成搬到瀏覽器端。
- 爬格子在參與者非常多時需要水平捲動；原版名單上限為 40 人。
- 目前一次最多抽三人；更大批次應改用不同視覺，不宜讓路徑過度重疊。
