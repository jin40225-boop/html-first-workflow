# schema 驅動的多階段表單引擎

## 這個功能幫我做什麼

**要改報名表的欄位時，不用叫工程師改程式。**

表單長什麼樣子存在資料庫的一筆 JSON 裡，網頁只是把它畫出來。要加一個欄位、改一句說明、把某一題移到第二頁，都是改那筆 JSON，不用重新建置、不用部署。

它撐得住的不只是「一堆欄位排下來」這種簡單表單，還包括三種以前只能硬寫的狀況：

- **分成好幾步**——第一步先選時段，選得到再花時間填資料，不浪費填表人的時間。上面有步驟指示器，每一步各自驗證。
- **同一組欄位可以填好幾筆**——「孩子的狀況」按一下「＋ 新增一位孩子」就多一組，最少幾筆最多幾筆自己設。
- **看情況才出現的欄位**——身份選「其他」才跳出「請說明」；選「單獨出席」就不會問「同行對象」。沒出現的欄位不驗證，也不會偷偷把舊答案送出去。

最後一定會有一頁「請確認填寫內容」，可以逐段跳回去改。

## 技術線

```
資料庫 form_schemas（一個專案一列）
  ├─ fields  jsonb   欄位定義陣列
  └─ stages  jsonb   階段標題與開場說明
        ↓ 讀出來就是 FormSchema 物件
   form-utils.ts（純函式，沒有 React）
     ├─ createAnswers()       依 schema 產生空答案
     ├─ fieldsForStage()      依 stage 分組
     ├─ isFieldVisible()      條件顯示判定
     ├─ validateAnswers()     只驗證「這一階段」且「目前看得見」的欄位
     └─ pruneHiddenAnswers()  送出前剔除隱藏欄位的殘留值
        ↓
   SchemaForm.tsx（畫面）        SchemaFormEditor.tsx（後台編輯同一份 schema）
     階段 → 欄位 → 確認頁            欄位增刪排序 ＋ 即時預覽
```

### 為什麼是 schema 驅動，不是為每張表單寫一個元件

| | 為每頁寫一個元件 | schema 存資料庫（本作法） |
|---|---|---|
| 改一個欄位 | 改程式 → 建置 → 部署 | 改一筆 JSON，馬上生效 |
| 後台要能編輯表單 | 做不到，除非再寫一套 | 天生就有，編輯的是同一份真相 |
| 三張報名表 | 三份會各自長歪的程式碼 | 一個引擎、三筆設定 |
| 新增一種能力（例如多階段） | 三個地方各改一次 | 引擎改一次，三張表都有 |
| 代價 | — | 引擎本身較複雜，且**能力上限被引擎綁住**：schema 只能表達引擎支援的東西 |

當初的判斷寫在原專案的施工紀錄裡：**不為新版報名頁寫一次性元件，而是升級引擎**——因為後台遲早要能編輯表單，一旦為某一頁寫死，資料庫那份 schema 就不再是唯一事實來源，兩邊會分岔。

## 核心手法

### 一、條件顯示要管三件事，少一件就會出錯

`visibleWhen` 只是一個判定函式，真正麻煩的是它牽動三處，而且很容易只做第一處：

```ts
// form-utils.ts:34  判定本身很短
export function isFieldVisible(field: FormField, answers: FormAnswers): boolean {
  const condition = field.visibleWhen;
  if (!condition) return true;
  const other = answers[condition.key];
  if (Array.isArray(other)) return other.some((item) => typeof item === 'string' && condition.equals.includes(item));
  return typeof other === 'string' && condition.equals.includes(other);
}
```

1. **不顯示**——`SchemaForm.tsx:38` 過濾要畫的欄位。
2. **不驗證**——`validateAnswers()` 開頭 `if (!isFieldVisible(...)) continue`。漏掉這行，使用者會被一個他看不到的必填欄位擋住，而且畫面上不會有任何紅字，只能重填。
3. **不送出**——`pruneHiddenAnswers()`。漏掉這一步的症狀最陰險：使用者先選「其他」填了說明，又改回「母」，那句說明還留在答案裡跟著送進資料庫。

第 2 與第 3 點是這個功能最值得抄的地方。

### 二、可增減群組的錯誤鍵：`群組key.索引.內層key`

群組的答案是「物件陣列」，所以錯誤訊息不能只用欄位 key，否則三個孩子的「年齡沒填」會互相覆蓋成一則。

```ts
// form-utils.ts:81
checkOne(sub, item[sub.key], `${field.key}.${index}.${sub.key}`, errors);
```

畫面端用同一個規則組出 key（`SchemaForm.tsx:177` 的 `keyPrefix`），兩邊對得上，第 2 個孩子的錯誤就只會出現在第 2 個孩子的那格。子欄位本身也吃 `visibleWhen`，判定的對象是**那一筆群組內容**而不是整張表。

### 三、確認頁不能給人看機器值

原本確認頁的「欲報名場次」顯示的是場次 UUID，因為選項值存的是 id。修法是在攤平時把值對映回標籤：

```ts
// SchemaForm.tsx:133
function flatten(value: FormAnswer | undefined, field?: FormField): string {
  const labelOf = (raw: string) => {
    if (!field?.options) return raw;
    return normalizeOptions(field.options).find((option) => option.value === raw)?.label ?? raw;
  };
  ...
}
```

**選項用「值／標籤」兩欄而不是單一字串**，是讓這件事成立的前提。`normalizeOptions()` 同時吃舊的純字串選項與新的物件選項，所以既有 schema 不必一次改完。

### 四、額滿時段用 `disabled` 選項表達

`FormFieldOption` 帶 `disabled` 與 `disabledLabel`，前台把標籤接成「週三晚上（額滿）」並讓它不可勾。額滿是**資料的狀態**，不是把選項從 schema 裡刪掉——刪掉的話，已經選了那個時段的舊報名紀錄就顯示不出來了。

### 五、驗證只做瀏覽器等級，不做業務判斷

`checkOne()` 只驗必填、Email 格式、台灣電話格式（含 `+886`、市話）。名額夠不夠、時段有沒有截止，一律不在前端判——那是伺服器的事。前端擋的是打錯字，不是規則。

```json
{
  "react": "^18",

}
```

`lucide-react` 只有 `SchemaFormEditor.tsx` 用到（上移／下移／刪除／新增四個圖示）。只要前台表單的話，`SchemaForm.tsx` ＋ `form-utils.ts` ＋ `FormField.tsx` 三個檔零外部相依。

資料庫端需要 `jsonb` 欄位，PostgreSQL 或 Supabase 皆可；SQLite 存純文字 JSON 也能跑，只是不能在 SQL 裡查詢欄位內容。

## 已知限制

- **後台編輯器落後引擎一截。** `SchemaFormEditor.tsx:14` 的 `fieldTypes` 只列了 7 種型別，**沒有 `radio` 與 `group`**，也沒有 `stage`／`visibleWhen`／`subFields` 的編輯介面。也就是說：這幾項新能力目前只能靠改 SQL 設定，後台點不出來。要補的話是往 `FieldEditor` 加控制項，引擎端不用動。
- **群組不能巢狀。** `subFields` 裡再放一個 `group` 沒有測過，`emptyGroupItem()` 的型別（`Record<string, string | string[]>`）也擋著。
- **`visibleWhen` 只支援「等於其中之一」。** 沒有「不等於」「大於」「且／或」。真要複雜條件建議拆成多個欄位，不要把引擎養成規則引擎。
- **群組上限寫死 10。** `SchemaForm.tsx:157` 的 `field.maxItems ?? 10`，沒設定時就是 10。
- **沒有草稿續填。** `initialValues` 可以帶入既有答案，但沒有自動存檔；重新整理會全部消失。多階段表單愈長，這個風險愈明顯。
- **電話驗證是台灣格式。** `form-utils.ts:62` 的 regex 認 09 開頭手機與 0X 市話，跨國要改。
- **`FormField.tsx` 是壓成單行的寫法。** 一個函式一行，讀起來吃力，但確實能跑；不要為了排版重打，會有出入。
