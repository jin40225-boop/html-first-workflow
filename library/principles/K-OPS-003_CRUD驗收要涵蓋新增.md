# CRUD 驗收必須涵蓋「新增」，不能只驗「修改」

## 問題

一個場次管理功能，驗收清單六項全過：格內改名額、改截止日、上下架開關、改主題、改客座、改候選時段。全部實測、全部綠燈、簽收結案。

**兩天後使用者要新增一個場次——每一次都失敗。**

而且不是那兩天壞的。翻紀錄發現：**從功能上線的第一天起，新增就沒有成功過。**

根因是一行欄位對映：

```ts
slot_options: session.slotOptions ?? null
```

那個欄位在資料庫是 `not null default '[]'`。而**明確送 NULL 不會讓預設值生效**——預設值只在「欄位整個沒出現在 INSERT 裡」時才套用，送 null 就是直接踩 not-null 限制。

新場次的草稿沒有候選時段（`undefined` → `null`），所以每一次新增都失敗；既有場次讀回來是 `[]`，所以每一次修改都正常。

**同一段程式碼、同一個 payload、兩條路徑，其中一條可以整整壞掉，而另一條全綠。**

## 原則

**任何有「新增」與「修改」兩條路徑的功能，驗收清單必須各驗一次。**

理由不是為了完整性，是因為這兩條路徑**送出的資料形狀不一樣**：

| | 新增 | 修改 |
|---|---|---|
| 欄位來源 | 表單草稿，很多欄位是空的／沒有 | 從資料庫讀回來，每個欄位都有值 |
| 缺欄位的表現 | `undefined` / `null` | 資料庫的預設值（`[]`、`0`、`''`） |

修改路徑會**自動幫你把缺的欄位填滿**。它不是在測你的程式，它是在替你的程式遮醜。

## 做法

### 一、驗收清單逐條標記它驗的是 C 還是 U

不要只寫「場次管理 ✓ 六項」。寫成：

```
[U] 格內改名額     [U] 改截止日     [U] 上下架
[U] 改主題客座     [U] 改候選時段   [C] 按下新增   ← 這一項當初不存在
```

一眼就看得出缺哪個字母。

### 二、用「畫面上那顆鈕實際送出的物件」做斷言，不要用手寫假資料

這是最關鍵的一條。

```ts
// ✗ 手寫的完整假資料——它會自己把缺的欄位補齊，正好繞過這個 bug
const fake = { id, projectId, title, startsAt, endsAt, capacity, status,
               slotOptions: [], instructorIds: [] };

// ✓ 逐字取自「新增」按鈕實際建立的那個草稿物件
const draft = { id: `draft-${uuid}`, projectId, title: '新場次（請改標題）',
                startsAt, endsAt, capacity: 1, bookedCount: 0,
                status: 'closed', instructorIds: [] };   // ← 沒有 slotOptions
```

假資料測起來會全綠，真實路徑照樣壞。**這個坑踩過不只一次**：另一次是用新版欄位格式的假資料測表格，真實資料是舊版平面欄位，於是整欄顯示「—」而測試全綠。

判準：

> 這份測試資料是我打出來的，還是從真的會送出它的那段程式碼複製過來的？

### 三、把欄位對映抽成可匯出的純函式

```ts
export function sessionRowFor(session) { return { …欄位對映… }; }
```

抽出來才測得到。原本它藏在 `adminSaveSession` 裡面，而那個函式要連資料庫才跑得動——於是永遠沒有人測它。

### 四、順手掃一次同型的欄位

發現一個「明確送 null 給 not-null default 欄位」之後，把同一個 payload 裡其他 `?? null` 全部對照 DDL 檢查一次。同型的坑很少只有一個。

也要注意近親：**欄位可為 null 但有預設值**（例如 `default auth.uid()`）。送 null 不會報錯，但會靜靜存進 null，把「誰做的」弄丟。

### 五、寫進基準文件，不是只修掉

這種缺陷的根源是**驗收方法的缺口**，不是那一行程式。修完那行，下一個功能還是會用同樣的清單驗。要把「CRUD 各驗一次」寫進專案的驗收紀律裡。

## 為什麼值得寫下來

「共用同一段程式的兩條路徑，其中一條可以整整壞掉而另一條全綠」——這句話反直覺到，即使講過一次，下次還是會忘。

而且這個 bug 的存活期特別長：它不會報錯給開發者看（是使用者當場被擋住才發現的）、不會出現在監控裡（沒有人監控「新增成功率」）、而且**每一次修改成功都在強化「這個功能是好的」這個印象**。
