# 介面說出口的保護，交付當下就要存在

## 問題

一個「自訂分類」功能上線。系統預設的分類由自動流程維護，不該被改名或刪除，
這道保護設計在兩個地方：前端不給按鈕，資料庫用 trigger 擋。介面上因此寫著：

> 系統分類由流程自動維護，因此不可改名或刪除（**資料庫層也擋著**）。

但那支 migration **待審未套用**，功能卻先上線了。於是有一段時間，正式站上這句話是假的——
資料庫層什麼都沒擋，唯一的阻力是前端那顆不存在的按鈕。

裁決很直接：**這比一般的假功能更糟。** 假功能是「按了沒反應」，使用者馬上知道；
這個是「告訴使用者有保護，實際上沒有」——看到那句話的人會**放心去點**。

## 原則

**說明文字與它描述的機制，要在同一次交付裡落地。不能一個先上、一個等審。**

「不做假功能」通常被理解成「不要做按了沒反應的按鈕」。但它的另一半更容易被忽略：
**不要在介面上宣稱一個尚未存在的保證**。前者浪費使用者一次點擊，後者改變他的風險判斷。

## 做法

### 一、保護與描述綁成同一個交付單位

如果變更的 UI 文案寫了「資料庫層也擋著」「已加密」「無法復原」「會自動備份」，
那個機制就必須在同一次交付裡；不能它待審、文案先上。

若機制真的要等，**文案要先寫成當下為真的版本**
（例如「目前僅介面限制，資料庫層保護待套用」），等機制落地再改寫。
**誠實的暫時說法不會傷人，樂觀的預告會。**

### 二、過期的免責聲明與假功能一樣會誤導

反過來也成立。某個設定原本標示「這個門檻現在只是存起來，下一階段才生效」——
那句話在當時是誠實的，但功能接線之後就變成不實敘述，使用者會以為改了沒用而不去改。

**說明文字要跟著功能走。** 功能上線時要順手檢查：有沒有哪句話因此變成假的？

### 三、保護放在資料庫層，不只是 UI

UI 擋得住按鈕，擋不住直接打 API——**而擋不住的那條路，正是出事時沒有人看著的那條**。
凡是「不可以」的規則，能放進資料庫約束或 trigger 的就放進去；
UI 只是把它變得好用，不是把它變成真的。

### 四、狀態旗標的守門要擋兩個方向

本案的 trigger 第一版把整段旗標檢查包在「若舊值是受保護的」條件裡面，
於是只擋「受保護 → 不受保護」，反向沒擋。後果是死結：一筆資料被誤設成受保護之後，
既改不回去（那時舊值已是受保護）也刪不掉，只能再下一支 migration 解。

**寫成無條件比較**（`新值 ≠ 舊值 → 拒絕`），而不是包在「舊值是什麼」的條件裡。

### 五、把說明文字列入自動守門

既然文案本身是承諾，就讓它像程式一樣被檢查：把關鍵句列入 CI 斷言，
拿掉說明等於拿掉功能宣告。反過來，**當機制改變時，斷言會強迫你一併更新文案**——
上面第二點那個過期的免責聲明，就是這樣被抓到的。

## 為什麼值得寫下來

因為它是「不做假功能」這條原則裡最容易漏掉、後果卻最重的那一半。
死按鈕的成本是一次困惑；假保護的成本是**使用者依據錯誤資訊，做了他原本不會做的事**。

而且它有一個好認的觸發時機：
**每當你在介面上寫下一句關於「安全」「不可逆」「自動」的保證，
就是該回頭確認那個機制存不存在的時候。**
