# 沒有錯誤不等於有做到

## 問題

一週之內，同一個形狀的缺陷用三種面貌出現：

**一、註記從來就存不進去。** 新增內部註記時同時送了兩個關聯目標，違反資料表「三選一」的約束，
每次請求都被資料庫回 400。但那個處理函式**沒有 catch**，被拒絕的 promise 沒有人接——
**畫面看起來跟成功一樣，輸入框甚至清空了**。功能上線後沒有人回報，直到有人打開 network 面板。

**二、刪除回 0 列被當成成功。** 批次刪除只檢查了 `error` 沒檢查影響列數。
PostgREST 在 RLS 濾掉整批時**不報錯，只回 count 0**，畫面於是平靜印出「已刪除 0 個對話」，
而資料還在。

**三、刪資料不回收計數。** 計數的遞增掛在 INSERT trigger、回收掛在狀態轉換函式，
DELETE 沒有任何對應。刪掉之後總數正確、場次的已佔用數仍停在舊值——而那個數字直接決定
前台顯示的剩餘名額。

三者的共同點：**失敗與成功在畫面上長得一模一樣**。沒有紅字、沒有例外、沒有任何要人注意的東西。

## 原則

**「沒有拋錯」不是「有做到」的證據。要驗的是效果，不是有沒有例外。**

寫入型操作至少要回答三個問題，缺任何一個就會有一種失敗變成靜默：

| 問題 | 沒回答的後果 |
|---|---|
| 有沒有拋錯？ | 錯誤被吞掉，使用者以為成功 |
| **影響了幾列？** | 權限濾掉整批時回 0 列且不報錯 |
| **有沒有人把結果顯示出來？** | 前兩者都對，但畫面不更新也不報錯 |

## 做法

### 一、檢查受影響列數，不只檢查 error

```js
const { error, count } = await db.from('x').delete({ count: 'exact' }).in('id', ids);
if (error) throw new Error('刪除失敗：' + error.message);
if (count === 0) {
  throw new Error('一列也沒有刪除——請求被接受但沒有任何一列符合，通常是權限濾掉了。');
}
```

在 PostgREST／Supabase 這類「RLS 是過濾不是拒絕」的架構下特別重要：
**被過濾掉的請求在協定層是成功的。** 同樣的檢查也適用於 UPDATE。

### 二、每個寫入路徑都要有人接住錯誤

`await write()` 沒有 try/catch，就是一個沒人接的 rejection。
同一個檔案裡若已有共用的錯誤包裝器（`run(id, action, message)` 那種），交給它；
沒有就地補 catch → 顯示錯誤。**「反正也不會失敗」不是理由——上面第一個案例就是每次都失敗。**

### 三、用掃描器找出「這一類」，而不是修完眼前這一個

判準：**await 了會寫入的函式，卻沒有 try/catch 或 .catch。**

掃描器要分兩段：先從 api 層找出真的會寫入的函式（含只是轉呼叫的包裝），
再掃 UI 的四種呼叫模式——具名 async 函式、JSX 匿名處理函式、`void f()`、
`f().then()` 未接 `.catch`、以及 `useEffect` 內的非同步寫入。

⚠ 掃描器要認得**共用錯誤包裝器**，否則它會把已經被接住的寫入一直報成缺陷，
久了報告就沒人看。判準寫成「這個 await 是不是落在傳給包裝器的參數裡」，
而不是硬編某個函式名的特例。

### 四、計數器的每一條變動路徑都要對稱

遞增在 A 路徑、遞減在 B 路徑，就一定有一條 C 路徑沒人管。
補的時候要防重複扣：用一個「這筆是否還佔著」的欄位當守門，
否則對已經釋放過的資料再扣一次，**會吃掉別人的額度而且沒有錯誤訊息**。

## 為什麼值得寫下來

因為這一類缺陷**不會被回報**。使用者不會說「它壞了」，他會以為存好了，
然後在幾週後發現東西不見。會發現它的只有兩種情況：
有人剛好打開 network 面板，或者有人去數資料庫。

而修法的成本極低——多解構一個 `count`、多包一層 try/catch。低到不值得跳過。
