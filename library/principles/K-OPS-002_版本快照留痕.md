# 版本快照留痕

## 問題

跟 AI 協作改一個大檔案（一個 2000 行的頁面、一支 50 KB 的模組），改完發現不對——**想回到改之前的樣子。**

git 可以，但實務上有幾個情況 git 幫不上：

- 改了三輪、每輪都 commit 了，但你想比的是「第一輪之前」與「第三輪之後」的**特定幾個檔案**
- 你想同時開著新舊兩版對照看，不是看 diff
- 交接給別人時，要指著說「這是改版前的樣子」

## 原則

**大改之前，把要動的那幾個檔案複製一份到 `version_snapshots/`，用「日期＋這次在改什麼」命名。**

實例（取自 `社工共構觀庭筆記平台` 與 `court-notes-projection-site`）：

```
version_snapshots/
  2026-04-04_pre-overhaul/
    app/page.tsx
  2026-04-05_homepage_modular_snapshot/
    00-app-page.latest.tsx
  2026-04-05_homepage_guide_shelf_snapshot/
    00-app-page.latest.tsx
  2026-04-05_sessions_status_snapshot/
    00-SessionsOverviewSection.latest.tsx
    02-app-page.latest.tsx
  2026-04-06_sources_shelf_home_forum_sync/
    00-homepage.latest.tsx
```

## 命名規則拆解

```
2026-04-05_sessions_status_snapshot / 02-app-page.latest.tsx
└─ 日期 ┘ └── 這次在改什麼 ──┘   └序號┘└ 檔名 ┘└ 版本標記
```

- **日期在前** → 資料夾自然按時間排序
- **主題用英文 snake_case** → 一眼看出那次在動什麼
- **檔名前綴序號** → 同一次快照裡多個檔案的閱讀順序
- **`.latest`** → 標記這是該次快照的最終狀態（相對於過程中的中間版本）

## 為什麼值得寫下來

因為它**看起來是「不會用 git 的人才做的事」，但實際上解的是 git 不擅長的問題**。

git 的單位是「整個 repo 的某個時間點」。
版本快照的單位是「**這幾個檔案，在做這件事之前/之後**」——那是人的工作單位。

跟 AI 協作時特別有用：AI 一次改動的範圍常常很大，而且改完的東西你要讀過才知道對不對。
有一份改版前的副本擺在旁邊，比 `git diff` 好讀得多（尤其是大檔案、大幅重寫的情況）。

## 三條實務規則

### 一、只存「這次要動的」，不是整個專案

快照不是備份。存三個檔案就好，不要複製整個資料夾——不然幾次之後磁碟就滿了，而且找不到重點。

### 二、主題名要寫「在改什麼」不是「改了什麼」

`pre-overhaul`（大改之前）、`homepage_modular_snapshot`（首頁模組化那次）——
**看名字就知道那次的意圖**，不用打開檔案。

### 三、定期清理，不要無限累積

快照的價值隨時間急速衰減。三個月前的快照幾乎不會有人回去看。
**做完一個階段就把舊快照刪掉或壓縮封存**，git 裡有完整歷史，快照只是工作期間的便利。

## 與其他慣例的關係

- `K-GOV-001 預覽與提交分離` — 那是「改資料前先預覽」，這是「改程式前先留樣」，同一個保守取向
- `F-JOB-001` / `F-DB-003` 的備份 — 那些是自動的、系統層的；這個是手動的、工作層的
- `F-AI-002 VBA 專案模組盤點` 的相似度偵測 — **快照累積久了就是那個問題**：一堆看起來很像的檔案，不知道哪些是重複的
