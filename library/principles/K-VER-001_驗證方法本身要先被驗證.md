# 驗證方法本身要先被驗證

## 問題

三次「查證做了、結論卻是錯的」，而且每一次的錯誤都以**自信的正確答案**形式出現：

**一、掃描器漏掉它自己要抓的東西。** 為了找出「未接住的寫入」而寫的掃描器，第一次執行回報 1 處。
實際上它的正規式從左往右比對，`if (confirm('…')) void f(x).then(` 這種寫法裡，
惰性比對會從 `confirm(` 一路吃到 `f(x)`，於是呼叫者被認成 `confirm`、真正的 `f` 被吞掉且永不再檢查。
改成從 `.then(` 往回走括號配對後，同一份程式碼抓到 3 處。

**二、只比對子目錄就宣告「可安全刪除」。** 清點一份舊副本時，兩個獨立的視窗都只比對了 `src/`，
都得出「只有 2 個獨有檔案」的相同結論。改用全樹比對（排除 `node_modules`／`.git`／`dist`）後
實際有 **16 個**，其中五個是版控排除、**git 歷史完全不存在的個資檔**。差一點就把唯一副本刪掉。

**三、守門只擋一半的寫法。** 一支「不得寫檔」的腳本，守門列了
`writeFileSync|appendFileSync|createWriteStream`——`fs/promises` 的非同步版完全不在範圍。
而「把它改寫成 await 版」正是那種腳本最可能被改動的方向。

**四、拿 API 的錯誤當成資料庫的事實。**（2026-08-10 補）
推完一支 migration 之後，用 API 查新欄位得到 `42703 column ... does not exist`，
於是宣告「migration 沒套用」。實際上欄位已經在資料庫裡了——回報找不到的是 **API 層的
schema 快取**，它靠 DDL 通知重載，中間有幾秒到幾分鐘的落差。等一下重查就有。
**那個錯誤碼只證明「API 現在看不到它」，不證明「資料庫沒有它」**，而這兩件事被我當成同一件。

**五、測試工具的預設值偽造了結論。**（2026-08-10 補）
用 REST 端點送測試寫入來驗證守門，收到 `42501 RLS violation`，判定為「寫入政策擋下」。
實際擋的是**回傳那一步**——預設的 `Prefer: return=representation` 會執行
`INSERT ... RETURNING`，而匿名角色沒有讀取權限（這是對的），於是整筆回滾。
**寫入條件根本沒被評估到。** 改成 `return=minimal` 才測到真正要測的東西。

**六、守門在跑，但它的檢查範圍是零。**（2026-08-12 補）
一個 monorepo 的兩個子專案，`typecheck` 腳本是 `tsc --noEmit`，每次都綠。
但它們的 `tsconfig.json` 是 solution-style——`"files": []` 加上只有 `references`。
`tsc --noEmit` 照著那份設定去查，**查了零個檔案**，所以必然通過。
真正會檢查的是 `build` 裡的 `tsc -b`，而完整檢查指令不含 build。
實際後果：其中一個子專案的正式建置**從第一天起就是壞的**（兩個真實型別錯誤），
沒有任何人發現，因為守門一直是綠的。改成 `tsc -b --force` 才驗得到。

**七、清點工具靜默漏掉它該數的東西。**（2026-08-12 補）
用 PowerShell 的 `Get-ChildItem -Recurse` 清點一個資料夾，得到 13,109 個檔案；
`robocopy` 對同一個資料夾數到 13,674。**差了 565 個，而且沒有任何錯誤或警告**——
遇到超長路徑就跳過（配上 `-ErrorAction SilentlyContinue` 更是完全無聲）。
拿它的數字去比對來源與備份，會得到「一致」這個錯誤結論。

## 原則

**一個查不到東西的檢查，與一個壞掉的檢查，外觀完全相同。**

所以任何要拿來下結論的檢查，在相信它之前，要先證明它**分辨得出差異**。

## 做法

### 一、反向對照組：拿已知有問題的狀態餵給它

最省事的做法是拿**修正前的版本**當對照組：

```
對施工前的 commit 跑 → 應該抓到 N 處
對現況跑             → 應該是 0 處
```

兩邊都是 0，代表工具壞了而不是問題不存在。這一步花不到一分鐘，
卻是「零發現」這個結果**唯一的意義來源**。

守門斷言同理：**注入 → 紅燈 → 還原 → 綠燈**。沒有走過紅燈的守門，等於沒有守門。

### 二、檢查範圍要涵蓋全域，不是問題描述的範圍

被問到「這兩個檔有沒有問題」時，答案往往是「這一類檔都有問題」。
先全站掃描再下結論，不要只查被指到的那幾個——
**照著問題描述的範圍去查證，會產出一個對錯誤集合的自信答案。**

比對兩份目錄時，比對 `src/` 不等於比對整個專案。排除建置產物就好，不要再縮範圍。

### 三、守門若以 API 名稱列舉，要問「同一件事還有沒有別的寫法」

同步／非同步、不同模組路徑、別名匯入——每一種都是同一件事的另一個寫法。
**擋住一種寫法而放過另一種，比沒有守門更危險，因為它讓人以為擋住了。**

「另一個寫法」不只出現在 API 名稱上，也出現在**資料的表示法**上。
路徑、識別字、重新導向目標這類會先解碼再判斷的值，一定要測**編碼過的變體**
（`..%2F`、`%2e%2e`、`..%5C`）——未編碼的形式往往在到達守門之前就被客戶端正規化掉了，
**只測未編碼版本等於沒測那條守門**。展開見 `K-VER-003 同一個決策的兩半要用同一個表示法`。

### 四、分辨「讀不到」與「不一樣」

雜湊比對工具遇到雲端同步的佔位檔會失敗，錯誤訊息是「雲端檔案提供者未執行」。
若把它當成「內容不同」，就會得到一個完全錯誤的比對結果。
**工具回報失敗時，先確認它是「讀不到」還是「讀到了但不同」。**

### 五、分辨「工具說沒有」與「東西不存在」

上面第四、第五個案例是同一種病：**把中介層的回應當成底層的事實**。
API 的快取、SDK 的預設值、CLI 的離線模式——每一層都可能在你和真相之間回答問題。

實用的判準：**這個否定的答案，是誰說的？**
- 資料庫說沒有 → 可信
- API 說找不到 → 只代表 API 現在看不到
- 工具回錯誤 → 先確認錯誤是「目標拒絕」還是「工具自己的限制」

分辨的方法通常很便宜：換一條路徑再問一次（等幾秒重查、換一個回傳模式、
直接查底層）。**兩條獨立路徑得到同樣答案，才把它當結論。**

### 六、改完檢查工具要重跑反向對照

修正誤報、放寬條件、加白名單——每一種都可能把偵測能力一併關掉。
改完之後對照組要再跑一次：**對照組仍抓得到，才代表你只修掉了誤報。**

## 為什麼值得寫下來

因為這一類錯誤的代價不對稱。一個漏抓的掃描器只是白做工；
但一個「已驗證可安全刪除」的錯誤結論，後面接的是不可逆的動作。
上面第二個案例若照著錯誤結論執行，會刪掉五個版控歷史裡不存在的個資檔——那是唯一副本。

而反向對照組的成本是一分鐘。
**任何要用來支撐不可逆決定的檢查，都值得先花這一分鐘。**
