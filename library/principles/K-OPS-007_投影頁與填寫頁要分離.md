# 投影頁與填寫頁要分離

## 問題

活動現場常會同時需要兩種畫面：參與者用手機填自己的狀態，主持人把全場狀態投影出來。這兩個畫面看起來都在處理同一份資料，很容易被做成同一頁，只靠角色判斷或條件區塊切換。

但真實使用時，兩邊的壓力完全不同。填寫頁需要讓參與者專心完成自己的卡片；投影頁需要讓主持人和全場在遠距離一眼看懂現在發生什麼。若共用同一個外殼、說明文字、導覽與卡片節奏，最後會變成參與者被資訊干擾，主持人又看不到真正要看的狀態。

在活動同步狀態板的實體測試前，填寫頁已經被收斂成單張狀態卡；投影頁則需要放大目前階段、突出未確認更新、支援點開學員卡協助自我介紹。這不是版面美化，而是兩個現場任務。

## 原則

**共用資料流，不共用操作畫面。**

同一套 API、欄位契約與 Google Sheets 後端可以共用；但只要使用者、裝置、觀看距離與決策任務不同，畫面就應該分開設計。

- 填寫頁服務的是「一個人、手機、小螢幕、快速送出」。
- 投影頁服務的是「一群人、投影幕、主持人掃描、現場確認」。
- 主持控制可以存在，但不應壓過投影主畫面。

判準很簡單：如果一段文字、按鈕或卡片只對其中一種角色有用，它就不該出現在另一個角色的主畫面上。

## 做法

### 一、路由先分清楚

至少保留兩個明確入口：

```
/join   參與者填寫頁
/board  投影頁
```

根路徑可以只做導向，不需要另做介紹頁。現場活動的第一螢幕應該直接進入工作，而不是讓使用者先讀一段網站說明。

### 二、外殼也要分開，不只是內容分開

填寫頁可以有較安靜的頁首、簡短提示、置中的表單和明確送出鈕。投影頁則需要更大的狀態文字、更寬的卡片網格、較少的導覽干擾，以及主持人能遠距離辨識的提示。

若只在同一個 `AppShell` 裡依路由換內容，頁尾、導覽、說明膠囊和背景節奏仍會把兩頁綁在一起。到實體測試階段，投影頁應該有自己的 shell。

### 三、投影頁以「現場確認」為主，不以說明為主

投影頁最重要的是：

1. 目前階段與主持指令。
2. 每位參與者的即時狀態。
3. 哪些卡片更新後尚未被主持人看過。
4. 點開卡片後能協助自我介紹或現場 cue 人。

說明類文字只留短提示，不另外開資訊卡。任何需要解釋才能操作的設定，都應收進主持控制抽屜或後台模式。

### 四、更新提示不能只靠短暫動畫

現場主持人可能正在講話、看別的視窗或處理器材。卡片更新後只閃幾秒，很容易錯過。

更穩的做法是：卡片變紅或發光，直到主持人點開確認。確認狀態可先存在本機 `localStorage`，代表「這台投影裝置已看過這個版本」。這比全域已讀更符合投影現場，因為被確認的是主持人的注意力，不是資料本身。

### 五、填寫頁允許窄更新，避免誤覆蓋

參與者臨時只想改「即時狀態」時，不應被迫整張表單重新送出。可以提供「只更新即時狀態」這種窄操作：用後端已儲存的其他欄位補齊請求，只改變 `status_text`。

這能降低一個常見風險：使用者在表單上試填了別的欄位，卻只是想改狀態，結果把尚未確認的變更一起送出去。

### 六、主持控制放在顯式模式

投影頁可以提供主持控制，但入口要明確，例如：

```
/board?admin=1
```

控制項放抽屜，不混進公開投影主畫面。這樣同一個投影頁可以在一般模式保持乾淨，在主持模式才打開設定。

### 七、正式上線要驗直達路由

若是 React/Vite 這類前端路由，上線後不能只驗首頁。一定要直接打開：

```
/join
/board
```

Vercel、Cloudflare Pages 或其他靜態部署都需要對 SPA 做 rewrite，否則現場分享直接網址時可能出現 404。

## 為什麼值得寫下來

這條經驗的價值在於，它把「同一份資料」和「同一個介面」拆開了。很多活動工具失敗不是因為後端不會同步，而是現場每個角色都被迫看一個折衷畫面。

分頁之後，參與者更快送出，主持人更容易掌握變化，投影畫面也不會被說明文字和設定項目稀釋。對小型活動、工作坊、課程、社群互動與臨時協作工具來說，這是一個成本很低但體驗差異很大的設計決策。
