# 全域功能要把顯示範圍與資料授權一起定義

## 問題

需求說「全域公告」時，很容易把「全域」理解成所有路由都渲染同一元件。但一個系統可能同時有
公開首頁與取得工作權限後的內部頁面；若只在版面層加元件，公開頁可能誤顯示內部內容；若只在
前端隱藏，匿名使用者仍可能直接呼叫資料 API。

另一個常見偏差是另建一套公告表與後台。當公告其實只是既有貼文的選填呈現方式，第二套資料
生命週期會讓封存、回收、權限與原文連結產生兩份真相。

## 原則

**「全域」必須先寫成授權範圍與路由集合，再決定元件放哪裡；資料可見性由 API 守，畫面範圍由
應用殼守，兩者各自 fail closed。若功能依附既有內容，就沿用既有內容的生命週期。**

這裡的全域可以是「所有內部工作頁」，同時明確排除公開首頁。排除不是例外補丁，而是需求契約。

## 做法

1. 把顯示範圍列成可驗證集合：公開入口、內部入口、登入／工作階段狀態、直接 API 存取。
2. API 先驗證授權，再查資料；匿名請求不可因前端通常不呼叫而被默認安全。
3. 應用殼依路由排除公開頁，避免曾登入的瀏覽器在公開入口仍看到內部元件。
4. 伺服器統一處理有效期間、排序與數量，讓每個內頁得到同一組結果。
5. 功能若是既有內容的選填模組，跟隨原內容的封存、刪除、板塊與原文連結；不要另造第二套後台。
6. 驗收至少包含：兩個不同內部頁面、公開首頁、匿名 API、有效／失效資料與返回原文。

## 為什麼值得寫下來

「全域」是一個產品範圍詞，不是 React 元件位置。只解畫面會漏資料 API，只解 API 又可能違反
公開首頁排除的核准需求。把授權與顯示拆成兩道可驗證守門，才能讓功能真的跨內頁，同時不擴大
資料揭露。

沿用既有內容生命週期也讓功能可組合：同一篇貼文未來可以同時啟用 QR、傳閱、投票或跑馬燈，
而不需要每加一種呈現就新增一套資料表與管理入口。

## 適用邊界

- 適用於同一站內同時存在公開與內部路由的公告、警示、導覽列、快捷列或狀態橫幅。
- 若公告具有獨立審核、法定留存或不同權限模型，另建資料模型可能才是正確選擇。
- 要把公開首頁納入顯示，屬資料揭露範圍變更，必須重新核可，不能只移除路由判斷。
