# 同一件事有兩個入口，遲早分岔

## 問題

同步作業改成分批之後，加了一段「按一次就把批次接連跑完」的迴圈，讓使用者不必按二十次。改完、部署、回報完成。

代驗結果：**每按一次仍然只前進 5 筆**。連續七輪，每一輪恰好 5，一次都沒有連跑。

一開始的假設是迴圈壞了。查程式碼——迴圈條件正確、回傳值正確、看不出任何理由會只跑一輪。花了一整輪來回才找到真正的原因：

**同步鈕有兩顆。** 一顆在收件匣、一顆在整合設定。迴圈只加在後者。使用者按的是前者，而前者仍然是「送一次請求就結束」的舊寫法。

程式碼沒有 bug。**功能有兩份實作，只改了一份。**

## 原則

**同一件事出現第二個入口的那一刻，就要決定：合併，還是明確接受它們會分岔。**

沒有第三種選項。「兩邊記得一起改」不是選項——那是把正確性寄託在記憶力上，而記憶力會在半年後、換人接手時、或同一個人很累的那天失效。

值得注意的是：**分岔通常不是在複製當下發生的，是在後續某一次單邊修改時發生的。** 複製的那一刻兩份是一樣的，看起來沒問題。所以「複製時沒事」不能當作不處理的理由。

## 做法

### 一、抽成共用實作，兩個入口都呼叫它

```
src/…/gmailSync.ts
  syncGmailUntilDone(full, onProgress, shouldStop)   ← 唯一一份迴圈
      ↑                    ↑
  收件匣的按鈕        整合設定的按鈕
```

共用函式要把「畫面怎麼呈現」留給呼叫端（`onProgress` 回呼），否則兩邊會為了顯示差異又各自複製一份。

### 二、加一條斷言擋住它再分岔

**這一步比修好那一次更有價值。**

```js
for (const page of ['收件匣頁', '整合設定頁']) {
  if (withoutComments(read(page)).includes('await triggerSync(full)')) {
    throw new Error('又出現單發呼叫；按一次必須把佇列跑完，不是前進一批');
  }
}
```

修掉的是這一次，斷言擋掉的是往後每一次。而且它會在**新增第三顆按鈕**的時候就叫出來——那正是最容易重演的時刻。

### 三、找第二個入口的具體方法

不要用回憶，用搜尋。以**被呼叫的那個函式名**去搜整個原始碼：

```
grep -rn "triggerGmailSync" src/
```

這次就是這樣找到的：搜出來兩處，一處在共用的 API 層，一處在另一頁的 handler 裡。**搜「行為」比搜「頁面」有效**——你不知道有幾個頁面，但你知道它們都得呼叫那個函式。

### 四、症狀對不上程式碼時，先懷疑「有第二份」

當「程式碼看起來明明會 A，實際觀察到 B」時，除了「我看錯了」之外，還有一個同樣常見的解釋：**你讀的不是正在執行的那一份**。

可能是另一個入口、舊的建置產物、另一個分支、快取住的舊版本。這些都比「迴圈語意錯了」更常見。

### 五、查不出來就不要假裝修好

這次在找到第二顆按鈕之前，曾經回報過一次「從程式碼看不出這個 bug」，並且改為**讓下一次可判讀**：進度顯示批次序號（「只跑一批」和「跑了 40 批」原本在畫面上長得一模一樣）、單批失敗不吞掉前面的成果並說出中止原因。

那些改動後來沒有直接指出根因，但它們讓第二次回報帶著更精確的證據回來。**在還不知道原因的時候，增加可觀測性是唯一穩賺的動作。**

## 為什麼值得寫下來

這類問題的代價不在修復——修復通常是十分鐘的事。代價在**診斷**：因為程式碼看起來是對的，所以所有人都會先懷疑邏輯、懷疑環境、懷疑框架，最後才想到「是不是有兩份」。

而它幾乎必然發生在**功能演進的時候**：原本只有一個入口，後來為了方便在另一個頁面也放一顆；原本只有一支腳本，後來排程和手動各跑一份。新增入口的那一刻沒有人覺得是在複製邏輯——因為當時的邏輯只有一行。
