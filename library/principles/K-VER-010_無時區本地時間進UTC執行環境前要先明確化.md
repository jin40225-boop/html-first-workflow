# 無時區本地時間進 UTC 執行環境前要先明確化

## 問題

HTML `datetime-local` 送出的是沒有時區的字串。台灣電腦在本機把「立即開始」解讀成台灣時間，
部署到以 UTC 執行的 Cloudflare 環境後，卻可能延後八小時。程式沒有報錯、資料也成功保存，
畫面只是一直等不到開始時間，因此很容易被誤判成刷新、跨頁狀態或「全域功能沒有接通」。

本機測試若沿用台灣時區，甚至會完整通過，因為錯誤只在另一個執行時區成立。

## 原則

**沒有時區的日期字串不是完整時間契約。它進入 UTC 雲端執行環境前，必須由系統明確指定原始
時區並正規化成 ISO；驗證要跨時區，不能用本機顯示正確替代正式環境。**

舊資料修復也要依可證明的錯誤形狀精準相容，不可把所有未來排程用固定時差一起搬動。

## 做法

1. 瀏覽器把 `datetime-local` 轉成帶 `Z` 或 offset 的 ISO 8601 後再送出。
2. 伺服器仍防禦性處理歷史或其他客戶端送來的無時區字串，明確加上業務時區，例如 `+08:00`。
3. 儲存與比較都使用同一時間基準；顯示時才轉回使用者時區。
4. 測試至少固定兩個不同時區執行，或明確注入時區解析器；不要依測試機系統設定。
5. 兼容舊錯誤時建立窄判準：本案例只在開始時間約等於建立／更新時間加八小時，且落在
   15 分鐘容差內才回推八小時。
6. 相容層先只影響讀取／計算；若要批次改寫正式資料，另行提案、預覽與核可。
7. 正式驗收要直接看 API 解析結果與跨頁可見性，不能只看資料庫有值或表單送出成功。

## 為什麼值得寫下來

這類錯誤的危險在於每一段都像成功：表單有值、API 200、資料庫有資料、本機測試綠燈。
真正失敗的是不同執行環境對同一個不完整字串做了不同推論。

把時區寫進契約後，問題從「依機器猜」變成「依規格算」；把舊資料相容限制在已知錯誤形狀，
則能修復已發生的八小時偏移，而不破壞使用者刻意安排的未來排程。

## 適用邊界

- 適用於預約、報名截止、公告排程、提醒、輪班與所有從 `datetime-local` 進入 UTC runtime 的資料。
- 不要假設所有使用者都在同一時區；多時區產品應保存使用者選擇的 IANA timezone 或 offset 契約。
- 15 分鐘容差與「建立時間加八小時」是本案例的舊錯誤指紋，不是可普遍套用的遷移規則。
