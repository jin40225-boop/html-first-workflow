# 確認要「驗得到」，不能只是「擋得住」

## 問題

一個會清空佇列的破壞性動作，照規矩加了確認：

```js
if (!window.confirm('清空同步佇列？…')) return;
```

擋得很好。人按錯不會出事。

然後代驗的時候——**點不到**。自動化瀏覽器遇到原生對話框會自動取消，所以那顆按鈕在自動化流程裡永遠不會生效。這個功能從此只能由使用者本人親手點，**任何形式的代驗都做不到**。

同一頁上還有幾個同樣寫法的動作：刪除範本、刪除回饋、未存變更切換。它們一起被關在門外。

## 原則

「破壞性動作要確認」和「這個動作要能被驗證」是**兩個都必須成立的需求**，不該互相犧牲。

原生對話框（`window.confirm`／`alert`／`prompt`）用一個實作同時滿足了前者、否決了後者。它看起來最省事，實際上是把整條驗證路徑賣掉換來的。

> 一個永遠無法被自動驗證的動作，等於每次改動都只能靠人肉重測——而人肉重測是最早被省略的那一步。

## 做法

### 一、確認做在頁面裡，兩段式

```
[清空同步佇列]                    ← 第一次點：切換成確認狀態
   ↓
[確認清空佇列] [取消]  + 警告文字   ← 第二次點：才真的執行
```

好處不只是可測：

- **警告文字直接顯示在頁面上**，不是藏在一個會被關掉的對話框裡
- 使用者可以一邊看警告、一邊看下面的實際資料再決定
- 與既有的「先看名單再寄出」是同一個形狀，介面語彙一致

### 二、非同步動作不要用 `window.confirm` 之外的原生阻塞

`alert()` 報結果、`prompt()` 要輸入，同樣的問題。結果用頁面上的訊息區塊，輸入用表單欄位。

### 三、加一條自動化斷言擋住它回來

```js
for (const page of [...]) {
  if (withoutComments(read(page)).includes('window.confirm')) {
    throw new Error('用了 window.confirm；自動化瀏覽器會取消它，這個動作將永遠無法被驗證');
  }
}
```

沒有這條的話，下一個人（包括 AI）寫新功能時的第一直覺仍然是 `window.confirm`——那是最短的一行。

### 四、既有的先不要一次全改

發現時同頁還有四處舊的。**在別人正在跑驗收的時候不要順手全改**——那會讓正在進行的驗證失去基準。列成獨立一輪處理。

## 為什麼值得寫下來

這條的特別之處在於：**它不是一個 bug**。`window.confirm` 完全正常運作，使用者體驗也沒問題。它只在「有人／有工具想要自動驗證這個功能」的時候才變成障礙——而那個角色在專案早期通常不存在，所以決定寫下 `window.confirm` 的那一刻，成本是零。

成本會在很久以後、由別人付。

一旦專案進入「AI 協作 ＋ 有代驗角色」的模式，介面選擇就多了一個以前沒有的評分項：

> 這個互動，除了人以外，還有誰需要能操作它？

同樣的問題也適用於：拖放操作、需要滑鼠懸停才出現的選單、只有鍵盤快捷鍵的功能、驗證碼、以及任何「只有畫面上看得到、程式讀不到」的狀態。
