# 預覽與提交分離

## 問題

自動化很好，但「自動」和「自動亂改」只差一線。
批次程式一跑就是幾千筆，跑錯了沒有 Ctrl+Z。

## 原則

**偵測、分析、產出報告 → 全自動。**
**動手改資料的那一刻 → 一定要人點頭。**

這條線不是畫在「危不危險」，是畫在「**會不會改變狀態**」。查詢再複雜也全自動，寫入再簡單也要核准。

## 三段式骨架

```
第一段：偵測 / 解析          全自動、可重跑、唯讀
第二段：登記 / 產出預覽       冪等、有去重鍵、仍然不改業務資料
第三段：落地                 需要人明確觸發，且預設關閉
```

第二段是關鍵，也是最容易被省略的一段。
它讓「**系統知道有這件事**」與「**系統據此改資料**」分離開來。少了它，你只能在「完全不做」和「做到底」之間二選一。

## 實作慣例

### 1. CLI 一律預設乾跑

```
node import.ts <檔案>              → 只印統計，什麼都不寫
node import.ts <檔案> --execute    → 才真的寫
```

**旗標的方向很重要**：要用 `--execute` 開啟寫入，不要用 `--dry-run` 關閉寫入。
前者手滑的後果是「什麼都沒發生」，後者手滑的後果是「資料被改了」。

### 2. 執行前自己備份

程式在 `--execute` 的第一件事是備份現有資料，並把備份路徑印出來。
不要假設使用者已經備份了。

### 3. 預覽輸出與正式輸出格式一致

乾跑印的統計，和正式執行印的統計，欄位要一模一樣。
這樣人才能對照「我預覽時看到的，跟實際做出來的，是不是同一件事」。

### 4. 程式化的異動不繞過稽核

系統自己做的修改，也要寫進變動軌跡，操作者標記為系統帳號。
「這筆是誰改的」永遠要答得出來，就算答案是「排程改的」。

### 5. 不猜

遇到判斷不了的情況（同名多筆、格式不符、兩邊值不同），**不要選一個看起來比較合理的**。
把它放進「待人工決定」的清單裡。

猜對了沒人感謝，猜錯了要花十倍時間查。

## 反面案例：什麼時候可以不走這套

- 純計算欄位的更新（例如重算完整率、更新逾期等級）——沒有語意判斷、天然冪等，可以全自動。
- 快取寫入（例如地理編碼結果）——寫錯了重跑就好，不影響業務資料。

判準：**如果寫錯了，能不能靠重跑修好？** 能，就可以自動；不能，就要人核准。
