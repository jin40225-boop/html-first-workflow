# 批次狀態遷移的順序與不刪除

## 問題

批次整理資料時，常見做法是「把不該出現的資料清掉，再把過期資料歸位」。這兩件事看起來都合理，但順序一反，結果就會變成污染。

例如活動場次資料裡同時有測試場次和過期場次：

- 測試場次應該除役，不該出現在公開歷史。
- 過期正式場次應該轉成已完成，進入活動軌跡。

如果先把所有過期場次轉成 `done`，再處理測試資料，那筆「過期的測試場次」就可能先被變成正式歷史，短暫或永久出現在公開畫面裡。

## 原則

**狀態遷移要先排除不該參與的人，再推進應該前進的人。**

而且除役不等於刪除。資料一旦參與過測試、上架、同步、統計或公開流程，就應該保留原因與時間，讓之後查得到「它為什麼不見了」。

## 做法

### 一、先除役例外，再推進一般狀態

批次遷移不要只看每條 SQL 本身正不正確，要看整組順序：

```sql
-- 步驟 1：先把測試、取消、錯誤建立的資料標成 cancelled
update sessions
set status = 'cancelled',
    admin_note = coalesce(admin_note || E'\n', '') || '除役原因...'
where title like '%測試%'
  and status <> 'cancelled';

-- 步驟 2：再把剩下的過期正式資料轉成 done
update sessions
set status = 'done'
where status in ('open', 'full')
  and ends_at < now();
```

第一步把不該參與公開軌跡的資料移出候選集合；第二步才處理正常生命週期。

### 二、不刪資料，改狀態並留原因

刪除會讓未來無法回答：

- 這筆資料是測試資料、取消活動，還是誤刪？
- 它曾經有沒有出現在公開畫面？
- 它為什麼沒有進入報表？

比較穩的做法是改狀態，例如 `cancelled`、`archived`、`retired`，並在備註或稽核表留下原因。

### 三、避免用脆弱條件直接自動跑大批資料

像 `title like '%測試%'` 這種條件是命名慣例，不是強約束。它可以用在小資料量、人工看過清單的場景；一旦資料量變大，就應改成明確欄位或人工核准名單。

### 四、批次遷移要能重跑

條件要寫成冪等：

- 已經 `cancelled` 的不要重複追加同一段備註。
- 已經 `done` 的不要再被下一輪改壞。
- 同一批次重跑時，統計數字應該可預期地變少或維持 0。

## 為什麼值得寫下來

這類錯誤不是單行語法錯，而是「每一步都對，但順序合起來錯」。

更麻煩的是，它通常發生在整理舊資料、上線前清資料、補歷史狀態這種一次性工作。一次性工作最容易少寫測試，也最容易被低估；但它碰到的常常是真資料，而且錯了會進報表或公開畫面。

把「先排除，再推進；不刪除，要留痕」寫成知能，之後遇到任何批次狀態遷移都能直接套用。
