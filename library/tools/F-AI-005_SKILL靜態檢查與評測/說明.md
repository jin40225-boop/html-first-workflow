# SKILL 靜態檢查與評測

## 這個功能幫我做什麼

**用測試來守住 AI 技能（SKILL.md）的品質。**

技能檔是純 Markdown，沒有編譯器、沒有型別檢查。寫壞了不會有人告訴你——
只會在某次真正需要它的時候，AI 沒有觸發、或觸發了但讀到一半發現連結是壞的。

這支 pytest 把「一個技能寫得對不對」變成**可以自動檢查的規則**。

## 八條檢查規則

```python
def test_expected_today_skills_exist()              # 該有的技能目錄都在
def test_skill_files_are_not_empty()                # 內容 > 500 字元
def test_skill_frontmatter_is_minimal_and_matches_folder()
def test_skill_files_include_trigger_and_workflow_language()
def test_openai_yaml_exists_for_each_skill()
def test_referenced_markdown_files_exist()          # ★ 本地連結不能斷
def test_skill_files_do_not_contain_obvious_secrets()  # ★ 不能夾帶金鑰
def test_deepeval_imports()                         # 評測框架可用
```

### 特別值得看的四條

**1. frontmatter 必須極簡且與資料夾同名**

```python
assert set(frontmatter) == {"name", "description"}       # 只准這兩個鍵
assert frontmatter["name"] == skill.parent.name          # name 必須等於資料夾名
assert len(frontmatter["description"]) >= 120            # 描述要夠長才帶得動觸發
```

`name` 與資料夾名不一致是最常見的失效原因——**技能載入不了，而且不會報錯**。
`description` 至少 120 字元的規則背後是：描述太短，AI 判斷不出什麼時候該用它。

**2. 內文必須含觸發語與流程語**

```python
assert "use when" in text
assert any(term in text for term in ["workflow", "process", "approval", "approve"])
```

強制每個技能都要交代「**什麼時候用**」與「**流程是什麼／要不要核准**」。
這兩件事沒寫清楚的技能，AI 用起來一定會走偏。

**3. Markdown 本地連結不能斷**

```python
for link in markdown_links(text):
    if "://" in link or link.startswith("#"): continue
    assert (skill.parent / target).exists(), f"Broken local markdown link in {skill}: {link}"
```

技能常常拆成主檔 + 幾個參考檔。**搬檔案或改名之後連結就斷了**，而 AI 讀到斷鏈只會靜默略過那部分。
這條測試把它變成會失敗的紅燈。

**4. 不能夾帶祕密**

```python
BLOCKED_TERMS = ["api_key","apikey","secret_access_key","private_key",
                 "BEGIN RSA PRIVATE KEY","BEGIN OPENSSH PRIVATE KEY"]
```

技能檔常常會貼範例指令，一不小心就把真的金鑰貼進去。技能又常常會分享出去。
**這是最後一道防線。**

## 附帶兩支 PowerShell

| 檔案 | 作用 |
|---|---|
| `run-skill-evals.ps1` | 761 bytes，跑評測（搭配 deepeval） |
| `install-all-skills.ps1` | 1.6 KB，批次把技能安裝到使用者的技能目錄 |

## 為什麼這條值得收

因為**它把「技能」當成有品質標準的產出物，而不是隨手寫的筆記**。

一般人寫技能是「寫完就丟進資料夾」。寫壞了、連結斷了、name 打錯了——
下次用到才發現，而且通常查不出原因（技能沒觸發不會有錯誤訊息）。

這八條規則的成本很低（一支 115 行的 pytest），但它讓技能維護從「靠記性」變成「靠 CI」。

**這也呼應 `F-DB-004` 裡那個手法**：用參數化測試強制「每個欄位都要寫進軌跡」——
**測試比自律可靠**，在這裡也一樣成立。

## 移植點

| 位置 | 要改的 |
|---|---|
| 第 7 行 `CODEX_SKILLS` | 技能目錄路徑。**Claude Code 的是 `~/.claude/skills`** |
| 第 9–17 行 `TODAY_SKILL_NAMES` | **換成你的技能清單。** 或改成自動掃描目錄，不用手動維護 |
| `test_openai_yaml_exists_for_each_skill` | Claude Code 不需要 `agents/openai.yaml`，這條可以刪掉 |
| `test_deepeval_imports` | 若不用 deepeval 就刪 |
| `BLOCKED_TERMS` | 依需要增補 |

**可以整段照抄的**：`parse_frontmatter()`、`markdown_links()`、frontmatter 三條斷言、觸發語檢查、斷鏈檢查、祕密掃描。

**建議的改良**：`TODAY_SKILL_NAMES` 是手寫清單，新增技能要記得加進去——**改成 `CODEX_SKILLS.iterdir()` 自動掃描**比較不會漏。

## 相依套件

```
pytest
deepeval   （只有 test_deepeval_imports 用到，不用可刪）
```

## 已知限制

- **只做靜態檢查**，不驗證技能實際跑起來會不會正確觸發。那要靠 `run-skill-evals.ps1` 那條評測線。
- 技能清單寫死。
- 檢查的是「格式對不對」不是「寫得好不好」。描述夠長不代表描述夠準。
