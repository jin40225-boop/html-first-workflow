# 軌道 B：協作確認台的寫作指引

骨架：`assets/review-console-template.html`

若專案有可實際操作的主要流程，預設改用 `integrated-review-workbench.md` 與
`assets/integrated-review-workbench-template.html`，把操作體驗和本確認台放在同一份 HTML。
本文件保留給沒有合理操作面的議題，或只需獨立決策確認的情況。

---

## 這份東西的目的

把 AI 腦袋裡的**理解、猜測、卡住的地方、還沒說的衝突**全部攤到一頁上，讓使用者用點的就能拍板。

它成功的判準只有一個：**使用者能不能只用滑鼠、不打字，就把整份核可完。**

---

## 固定八節，順序不可調換，缺的可留白但不能自己少一塊

**順序是三幕劇：先讓使用者看懂你要做什麼，才問他問題，最後講代價。**

| 幕 | 節 | 放什麼 | 常見錯誤 |
|---|---|---|---|
| **一、我懂了什麼、要做什麼** | **1 理解** | 複述使用者的指令與需求，寫成「我聽成的規則」 | 抄一遍他的話（沒有價值） |
| | **2 現況** | 已經做了什麼、還欠什麼、有沒有先斬後奏、查證到的事實 | 只講計畫不講已完成，使用者不知道自己核可的是什麼 |
| | **3 計畫** | 步驟、誰做、每步的驗收點 | 只有步驟沒有驗收點 |
| | **4 規格與元件** | 會用到的技術、套件、外部服務、參考來源 | 寫成技術炫技，使用者看不懂 |
| **二、我卡在哪、要你定** | **5 矛盾** | AI 知道但還沒解決的衝突 | 整節省略（最常見，也最傷） |
| | **6 提問** | 只有他知道的事 | 寫成問卷。真的沒得問就留白並說明 |
| | **7 決策** | 岔路題，每題附選項與推薦 | 選項沒寫影響與代價 |
| **三、代價** | **8 成本** | 見 `cost-and-tradeoffs.md` | 大手一攤列風險卻不給對策 |

### 為什麼是這個順序（2026-08-15 使用者裁決）

舊版把提問與決策放在計畫之前。使用者當場點破：

> 「你前面沒有給我看你目前的計畫，要怎麼依照計畫或理解對我提問？」
> 「前面沒有計畫或提案、方向，這裡我要拍板什麼？」
> 「我認為對我需求的理解擺第一，這樣才順。」

**計畫是提問的前置。** 使用者沒看到你打算怎麼做，就無法判斷你問的問題重不重要、也無法拍板。
這與依賴圖的「根在前、葉在後」是同一條原則的兩個層次：節與節之間也有依賴。

三幕之間不可交錯：第一幕全部是「我說」，第二幕全部是「你說」，第三幕是結帳。
使用者只要看到第五節開始，就知道「接下來是要我動的部分了」。

### 「現況」節：自曝其短是它的全部價值

如果 AI 在使用者核可之前就先動手寫了東西，**這一節必須講**，而且要給「作廢重寫」這個選項。
使用者有權知道他核可的是「還沒做的事」還是「已經做完的事」。

### 「矛盾」節：這節最容易被省略，也最值錢

寫進去的東西是：

- 使用者自己說過的兩句話互相打架（引用原文，兩句都貼出來）
- 使用者的規則跟工具的現實打架（例：他的 `AGENTS.md` 要求技能放 A 處，但工具只讀 B 處）
- AI 自己編的數字（例：「決策點 ≥3 才產確認台」的 3 是哪來的——**沒根據就要說沒根據**）
- 兩個技能／兩份文件的重疊與衝突

每則矛盾都要附**調和方案**，不能只是把矛盾丟出來。

---

## 12 則上限

**12 指的是「需要使用者決策的則數」。** 純資訊（現況、成本、規格說明）用收合呈現，不計入。

理由：使用者的稀缺資源是決策力，不是閱讀量。砍資訊會逼他在資訊不足下拍板，那更貴。

超過 12 則就是 AI 沒做功課——把該自己決定的技術取捨丟回去問了。回頭砍。

---

## 寫卡之前：先建依賴圖（草稿 ≥ 6 則時必做）

**這一節是整份指引最重要的部分。**

卡片一張一張想出來的確認台，一定會重複提問——因為每一題都是獨立想的，但它們實際上是一張有向圖。使用者的原話：「AI 在思考、規劃、提問時沒有意識到問題本身是有集群、歸屬、上下或關聯關係的，導致提問無法精準、重複的問題一直問。」

順序必須是：**列題 → 建圖 → 砍題 → 排序 → 才寫 HTML。**

### 第 1 步：攤平，填依賴表

把所有想問的先寫成一行式草稿，再對每一題回答兩個問題：

| 題 | 它的答案會改變誰？（下游） | 誰的答案會改變它？（上游） |
|---|---|---|
| Q1 客戶到哪一步 | U1 的答案、D1 的存廢、M2 的優先度 | 無 |
| D1 第一段做什麼 | P1 的內容 | Q1（拿到憑證→免問）、U1（選 C→免問） |

**偵測法：你自己寫的「→ 影響」欄就是依賴宣告。** 只要某個選項的影響欄裡出現另一題的編號或內容（「我會建議 U1 選 B」「可以跳過假 LINE 模擬層」），那就是一條邊，抄進表裡。**寫了影響欄卻沒抄邊＝漏建關聯。**

### 第 2 步：找根決策

對每一題數「它答了之後有幾題會免問或改推薦」（出邊數）。出邊最多、且自己沒有上游的就是根。

**根一定是事實題或意圖題**（「客戶簽了沒」「你這句話是什麼意思」），不會是技術題。一份確認台通常只有 1–2 個根。

找不到任何能消掉 ≥2 題的根、而題數又超過 8 → 代表你還沒想清楚，回第 1 步重來。

### 第 3 步：重複偵測（三個判準，中一個就處理）

1. **推薦重疊** —— 兩題的推薦選項展開後是同一份工作清單。
   > 真實案例：D1 推薦「假 LINE 骨架：資料表＋狀態機＋開單介面＋儀表板」，M1 推薦「只做不綁客戶的：狀態機、資料表、開單介面、儀表板」。**同一份清單，被問了兩次。**
   → 合併成一題，把兩個風險軸都寫進同一題的「為什麼這樣判斷」。
2. **事實—行動對** —— 一題問事實、另一題問行動，而行動可由事實映射得出。
   > 真實案例：Q1 問「客戶到哪一步」、U1 問「要不要開工」。
   → **只問事實**，行動寫成 `recommend` 連動規則；使用者只在不同意映射時才需要動行動題。
3. **互相引用** —— 兩題的選項說明互相引用對方 → 檢查是不是同一個決策的兩個切面。

### 第 4 步：排序

八節順序不動（那是使用者的裁決）。在**節內**照依賴排序：**根在前、葉在後，同集群相鄰。**

根通常天然落在「提問」節（事實題），而提問節排在決策節之前——順序會自動正確。
若根落在「矛盾」節（衝突的裁決會決定後面一串），也在決策之前，同樣正確。

### 第 5 步：合併門檻

- 三題共享同一個前置、且都只在前置的同一個值下有意義 → **併成一題**。
- 合併後選項會超過 4 個 → **不併**，改用 `mute` 連動。
- 合併後的題要註明「本題整合了原本會分開問的 X 與 Y」。

### 第 6 步：自我驗證（寫完 HTML 後逐條打勾）

- [ ] 每一條「影響欄提到別題」都有對應的 `.dep` 規則或 `data-rel`
- [ ] 每一張以「假設 X 選了 Y」開頭的卡（計畫卡最常見）都有對應的 `mute` 規則——**散文假設＝機器盲區**
- [ ] 走一遍根題的每個選項值，數還剩幾題要答；任一路徑下仍需全答＝連動白做了
- [ ] 沒有循環：A mute B 且 B mute A 一律是設計錯誤
- [ ] **12 則上限改按「最長必答路徑」計**：任一種答題路徑下，需要使用者實際處理的卡不得超過 12

## 關聯性的三種表達方式

### 啟用門檻（不要在小確認台上裝引擎）

| 檔次 | 條件 | 啟用什麼 |
|---|---|---|
| **不啟用** | 需決策卡 ≤ 4 且互不引用 | 什麼都不加 |
| **輕量** | 需決策卡 ≥ 5，或任一卡內文引用了另一卡 | 只加 `data-cluster`＋`data-rel`＋集群圖例（純標註、零 JS 邏輯、零風險）。**但建圖程序照跑**——它的主要產出是砍題，不是屬性 |
| **完整** | 需決策卡 ≥ 6，**且**建圖後存在至少一條真實的 mute 或 recommend 邊 | 全套引擎 |

### 屬性

| 屬性 | 放哪 | 表達什麼 |
|---|---|---|
| `data-cluster="money"` | `<article class="card">` | 集群歸屬（可跨節） |
| `data-rel="Q1 D1"` | `<article class="card">` | 弱關聯，渲染成可點的「相關」徽章 |
| `<div class="dep" data-when data-do>` | `.cbody` 之後、`.olabel` 之前 | 強連動規則，**元素內文就是人話理由，必填** |

條件式語法（只做三種形，夠用就停）：

```
Q1:line-ok            Q1 已答且選了 line-ok
Q1:signed|talking     選了兩者之一
Q1!cold               已答且不是 cold
U1:A+D1:fake          AND
```

效果：`data-do="mute"`（本題免答）／`data-do="recommend:X"`（把「我推薦」改到選項 X）。

**條件只對「選了哪個選項」判斷，不對標記（同意／不要）判斷。** 拿標記當條件會做出「你標了待議所以別題失效」這種使用者無法預期的行為。

**前置未答 ＝ 不觸發任何效果。** 使用者可能跳著答，不能因為他還沒碰根題就把葉題鎖起來。

### 兩條不可違反的呈現規則

1. **失效的卡片不能直接消失。** 要變暗、收合內容，但**原因橫幅永遠可見**，並附「仍要回答」按鈕與跳回上游改答案的連結。
   > 這不只是體貼。最大的風險是**錯誤的 mute 把該問的題滅音了**，使用者從頭到尾沒看到那一題——原因永遠可見才擋得住。
2. **匯出時必須快照「連動後生效的推薦」。** 既有規則是「沒意見＝照推薦做」，而推薦會被 `recommend` 連動改寫——不快照的話，AI 收到回覆時無法還原使用者默認的到底是哪個選項。

## 每一則的解剖

```
編號  類型徽章  [需要你回答]
標題（一句話講完，不用問號結尾）

內文：背景、我查到什麼、關鍵事實（表格優先於段落）
為什麼這樣判斷：AI 的推理過程 ← 必寫

選項標籤：「怎麼合併？」「模板放哪？」
  ○ 選項一  [我推薦]
      一行說明
      → 影響：選了會發生什麼    ← 必寫
      代價：會失去什麼、要多花什麼  ← 必寫
  ○ 選項二 …

整則判斷：✓同意 ✎要改 ✕不要 ◷待議
回覆欄（不填代表沒意見）
```

### 「為什麼這樣判斷」必寫

只給結論，使用者無法判斷該不該反對。把推理攤開，他才有辦法說「你這個前提就錯了」。
**這是確認台真正的價值，不是裝飾。**

### 選項的規矩

- 每題 **2–4 個**，超過就是沒收斂。
- **一定要標一個「我推薦」**，並在「為什麼這樣判斷」裡講清楚為什麼推薦它。
- **每個選項都要有「→ 影響」與「代價」兩行**，包括推薦的那個。推薦的選項也有代價，不寫就是不誠實。
- 不建議的選項要照樣寫完整，並直說「我不建議」與理由。**不要放稻草人選項**。
- 選擇選項只形成草稿，不自動視為「同意」。四態標記也只形成草稿；每題另按「保存本題」且成功後，才成為已保存意見。

### 提問的規矩

提問節只放**只有使用者知道的事**：他客戶的習慣、他的偏好、他的工作現場。
凡是查得到的、屬於技術取捨的，一律自己決定並寫進決策節。

提問也**必須附候選答案**，並寫清楚每個答案會導致什麼技術決定。

---

## 標記語彙：四態

`同意 ／ 要改 ／ 不要 ／ 待議`

「待議」不可省。少了它，使用者只能在同意與不要之間被迫二選一——那些被硬塞成「同意」的項目最容易出事。

---

## 回收：複製為主，下載為輔

- **「複製回覆給 AI」是主要通道**（沙箱可能擋下載，但剪貼簿多半可用）。
- 匯出的 Markdown 結構：依 `不要 → 要改 → 待議 → 同意 → 有補充` 分組，最後列出**未表示意見的編號**並註明「＝沒意見，照推薦的做」。
- 匯出內容最後要自動附上**給 AI 的驗收條件**（做法見 `軟體資料庫 F-AI-007`：把「什麼樣的產出會被退」一起講，AI 一次就對）。
- 一定要有「匯入先前 JSON」讓使用者續評。
- 頁尾要明講：草稿只存在這台的瀏覽器，換裝置或清快取就沒了。

---

## 視覺

**確認台固定用 `F-UI-001 暖色設計 token`**（軟體資料庫／介面元件）：暖米底、赭土紅、柔和圓角、字級 16–20px。
理由不是美感，是使用情境——降低長時間盯螢幕的疲勞。**這是使用者自己的風格，不要每次換。**

---

## 收到回覆之後

處理順序：**不要 → 要改 → 待議 → 同意**。

- 「待議」不得推進，改做不受它影響的部分，下一版重新提案。
- 使用者推翻了 AI 前提的地方，下一版要明講「我原本的判斷錯在哪」。
- 使用者說「這個你決定」的項目：**就決定**，並在下一則交付訊息裡說明裁決與理由。不准再問一次。

## 反面教材（這個技能被打出來的三次失敗，別再犯）

| 版本 | 犯了什麼 | 使用者的原話 |
|---|---|---|
| v1 | 23 則裡只有 5 則有選項，其餘要使用者打字；只談抽象流程，沒攤開實體布置、現況、矛盾 | 「妳的確認台根本不夠完善」「妳要讓我確認，有任何選項嗎？」 |
| v2 | 30 則裡一堆是把球丟回去問，沒寫影響與代價 | 「妳沒有說原因和影響、好的跟壞的，我無法決策」 |
| v3 | 內容用 JavaScript 生成，在會擋 JS 的檢視器裡整片空白；交付訊息又在對話裡複述了確認台裡的問題 | 「我沒看到啊？」「妳為何不用 HTML 提問」 |

三個教訓一句話：**能勾的就不要叫使用者打字；能自己查的就不要問；能寫死的內容就不要用程式生成。**
