# 設計規格 v1（主視覺與軟體介面）

> **版本**：v1 · 2026-10-15 負責人核可（「照草案」，含 Q-0～Q-5 代裁全照）。
> **檔案**：數值在 `assets/design-system/tokens.css`、元件在 `components.css`、可點範例在 `showcase.html`（先開它看）。
> **改這份規格**：只能走「規格升版提案」（見最後一節），不得在個別專案裡默默改值。

---

## 一、一句話與適用範圍

> 一套以個案為中心、像一套軟體在用的工作台：主畫面固定、字大好讀、動作就地完成；
> 系統先給預設、人保留最後決定；不比 Excel 慢、失敗一定出聲。

- **適用**：所有軟體與網頁介面——內部業務系統、對外網站、工具頁、確認台、綜合台的決策區。
- **不適用**：簡報、海報、影片（各有自己的風格技能）；客戶展示頁的「被展示系統」本身（照優先序第 3 條）。
- **新專案一律用本規格**（負責人親定）。

## 二、優先順序（遇到衝突照這個，由上往下）

1. **負責人已驗收滿意的畫面不回頭改。** 保有自己樣式的現役系統（例：主色不同、方形小圓角）維持原樣；
   只在負責人要求時換皮，換皮前先出「現行 vs 新規格」並排 HTML 給他挑，選定才施工（換皮不換操作）。
2. **專案已有自己的設計規格 → 照專案的。** 若那份規格是本規格的實例（自家前綴的 token），**數值必須與本規格一致**，名稱可以不同。
3. **客戶展示頁 → 模仿目標系統的長相**（見 `client-demo.md`）。
4. **其他所有情況 → 本規格。**

> 和舊資料的關係：`library/ui/F-UI-001_暖色設計token` 與 `F-UI-006` 是本規格的前身與來源之一，
> 數值有出入時以本規格為準。`assets/geo-playful-kit/` 只當**插畫與圖示素材庫**（問候、空狀態、人物），
> 它 `ui/` 裡的數值不用（Q-5）。
> `assets/` 裡既有的確認台／綜合台骨架目前還烤著 F-UI-001 的數值，尚未對齊本規格；
> 用骨架時決策區照骨架即可，**骨架之外新寫的介面照本規格**。骨架對齊列為待辦，不在本版範圍。

## 三、十條理念（附負責人原話）

| # | 理念 | 原話 |
|---|---|---|
| P-1 | **整合＝用起來像一套**，不是資料串通、不是把捷徑接在一起 | 「整合品質很低，這樣跟只是把快捷接在一起有何兩樣？」 |
| P-2 | **雙軌**：工作台一次處理我的全部個案；個案頁只浮出這一案的精準欄位；同一份資料、可互跳 | 「我要的是整合，不是閹割。」 |
| P-3 | **主畫面固定，動作就地完成**；會讓版面變長變亂的改浮動視窗 | 「盡量避免多視窗、多介面，而是在原本介面上就有可以的按鈕……只有要形成相關的追蹤表或綜觀核可，才會另有視圖介面。」 |
| P-4 | **系統是幫忙不是設關卡**：格式自動轉、照收、看不懂的標黃，不擋人 | 「輔助是要更方便不是限制」 |
| P-5 | **和 Excel 共存**：依目的當輔助、外掛或替代；改 Excel 正本要授權 | 「Excel 對大多數工作者才是最熟悉的」 |
| P-6 | **不能比 Excel 慢**：貼上是第一入口、下拉＋自填、打名字帶出整戶 | 「其實就是很簡單的關聯和下拉式表單的方法」 |
| P-7 | **畫面沒反應＝功能不存在**：失敗要出聲，版本由系統自己顯示 | 「不要讓 AI 幫使用者找版本；讓系統自己顯示版本。」 |
| P-8 | **系統給預設、保留人為操作空間**；每個決定留痕、可復原 | 「你本來的機制很不錯，可以預設。但也讓人為操作的空間存在。」 |
| P-9 | **個資只用到必要**，界線要具體，不做沒有對象的形式防護 | 「地址可以外送，但不能跟其他個資一起外送。」 |
| P-10 | **先用可操作 HTML 共同設計到滿意，再施工**；看重的功能要重做好；重構就是全新軟體 | 「……是因為不好用，所以導致使用率下降」 |

| 元件 | 規格 |
|---|---|
| 按鈕 | 高 ≥ 44、18px 粗 700、**膠囊**（圓角 999）、框 2px；小按鈕高 ≥ 36、字 ≥ 15（Q-0：通用形狀照膠囊） |

| 勾選框 | 22×22 |
| 篩選膠囊／頁籤 | 膠囊高 ≥ 36（字 ≥ 16）；頁籤 44–48（帶圖示 48）、計數紅點 |
| 狀態章 | 高 28、字 15 粗 800、膠囊 |
| 點擊目標 | 任何可點的東西 ≥ 36×36 |

### 形狀、間距、陰影

- 圓角：膠囊 999（按鈕／頁籤／篩選／章）・輸入 14・卡片 16・浮動視窗 18。
- 框線 2px；強調 3px；待處理橘框 3px。
- 間距 4／8／12／16／20／24；頁面左右 22px。
- 陰影三階：卡片、視窗、最前視窗（`--ds-shadow-card|window|front`）。

## 五、版面骨架（1440 桌機為準）

```
頂列：系統名・身分膠囊・◐・版本號（commit）
膠囊頁籤（帶計數紅點）——不用左側選單
問候橫幅：今天要處理什麼（有待辦才醒目，沒有就安靜）
數字卡一排（每格 ≥ 170px，最多 5–7 格，點了直接篩出那批）
全版大字工作區／清單（不限寬，左右 22px；閱讀型表單上限 1100px）
預覽、編輯、檢閱、明細 → 浮動視窗
```

**判準：主畫面高度與位置不變＝合格**（Q-1）。

- 短內容、看狀態 → 就地展開（只展開一列）。
- 要編輯、預覽、看歷史、內容長 → 浮動視窗。
- 開浮動視窗的按鈕必須長在原畫面那筆資料旁邊；浮動視窗不能變成新入口。
- 只有追蹤表與綜觀核可可以另立視圖。
- 區塊入口（例：成員／交通／餐食／備註）與「全部」並存，記住上次用哪個。
- 浮動視窗：可拖曳、不加遮罩、不鎖主畫面、沒有放大鈕；同時最多 4 個，第 5 個開時最早那個收到左下角工作列。
  預設寬：一般 520、工作型 780、報表型 1080。確認類對話框（真的要人停下來決定）才用遮罩。

## 六、操作規則（可逐條檢查）

- **R-01** 要：輸入用「下拉＋自填」，自填的值變成新選項；改成下拉時既有選項全部保留。
- **R-02** 要：打名字邊打邊跳「姓名(編號)・主責・狀態」，選定後帶出整戶並標來源。
- **R-03** 要：格式自動轉（西元→民國、補 0、小寫轉大寫），旁邊小字標「已轉換」；看不懂標黃「請確認」但照樣存。
- **R-04** 只擋：會寫錯人、算錯帳、破壞正本的情況；其他一律照收並標示。
- **R-05** 要：確認分三級（Q-2）——
  ① 單一可復原動作＝按了就生效＋提示裡有「復原」；
  ② 多欄編輯＝先暫存、按「儲存」才寫入，顯示「還有 N 處沒存」；
  ③ 批量、寫回 Excel、不可逆＝逐列確認表。
- **R-06** 要：失敗一定講原因（紅色提示，不自動消失）；成功提示 3 秒。不要：靜默略過、靜默隱藏功能。
- **R-07** 要：有待處理就用橘框＋數字＋「只看這些」，待處理排前面，但**預設畫面照樣顯示**。
- **R-08** 要：重要、常用的按鈕做大並附一行說明；**主按鈕一畫面只有一個**。
- **R-09** 要：刪除＝封存可還原；沖銷不刪除；每個決定留痕。
- **R-10** 要：個資只露必要——候選列只露遮罩線索（例如末四碼），不露完整電話地址；LINE 不放個資；截圖只用假資料。
- **R-11** 要：寫回 Excel 不讓 Excel 跳出來，寫完對帳才存；衝突時並排「原本／系統／Excel 新值」讓人選。
- **R-12** 要：系統標題列與浮水印顯示版本 commit；切回視窗自動檢查更新。
- **R-13** 要：匯出（PNG／LINE／Excel）用固定淺色票；A4 公文版型照單位現行範本。
- **R-14** 要：交付給負責人看——1440 桌機截圖、四行（資料夾／分支／commit／網址）、從他會點的入口實開、真環境驗收。
- **R-15** 要：要他自己跑的指令，先寫在哪跑，cd 單獨一個框，網址單獨一行。
- **R-16** 要：決策——他在場就在對話裡分批問（Q-3）；不在場才用 HTML 台，HTML 台只看操作、答案一定落檔由 AI 收回；不問他講過的規則。

## 七、不要這樣做（負責人退件過的）

| 做法 | 原話 |
|---|---|
| 多分頁殼只是並排各系統 | 「跟只是把快捷接在一起有何兩樣？」 |
| 個案頁把功能畫少 | 「我要的是整合，不是閹割」 |
| 另立入口、多一個查詢頁 | 「增加了兩個頁面轉換，這個完全可以在同一個頁面完成」 |
| 開功能就讓版面增生 | 「導致版面頁面增加，看起來反而混亂」 |
| 改版拿掉原本的區塊入口 | 「似乎改掉我本來的區塊做法，我希望區塊作法也要整合」 |
| 預設隱藏待處理的資料 | 「要顯示。只看待認領這個按鈕可以留下。」 |
| 用推測蓋掉原本的機制 | 「可以預設。但也讓人為操作的空間存在」 |
| 全線阻擋、整筆卡死 | 「這些鎖死制度也造成困難與不方便」 |
| 用使用量判定要刪 | 「是因為不好用，所以導致使用率下降」 |
| 重構案附應急補丁 | 「絕對不准救急、止血」 |
| 照規格直接施工、沒先共同設計 UI | 「我非常非常不滿意」 |
| 靜默失敗、給錯版本 | 「妳給我的閱覽版本都沒有這些！」 |
| 給手機版預覽 | 「給我預覽的以電腦版畫面為主」 |
| 只放 logo 和小圖示 | 「感覺不到美術」 |
| 傳統插畫、書籤風 | 「太俗、太老套」 |

## 八、怎麼用

1. 先開 `assets/design-system/showcase.html` 看長相與互動（可切深色、緊密版）。
2. 新頁面：複製 `tokens.css`＋`components.css`，`<body class="ds">`，元件 class 一律 `ds-` 開頭（對照 showcase 原始碼）。
   單檔離線交付時把兩份 CSS 內嵌進 `<style>`。
3. 已有自家 token 的專案：只對齊數值，不強迫改名（優先序第 2 條）。
4. 插畫、空狀態、人物圖：從 `assets/geo-playful-kit/` 拿素材；數值仍照本規格。
5. 交付前自查：本檔第四～六節逐條對一次；`validate_html.py` 照跑；1440 截圖用眼睛看一次（R-14）。

## 九、例外怎麼處理

- 規格沒寫到的情況：照十條理念推，**在交付訊息寫明「規格未涵蓋，我照 P-x 判斷」**，結案時列入升版提案。
- 規格寫到但這個專案做不到（例如宿主程式限制字型）：照做得到的最接近值，交付訊息寫明偏離哪一條、為什麼。
- 不得為了單一專案改 `tokens.css` 的值；專案自己的覆寫放專案裡。

## 十、規格升版提案（結案時做）

結案「留不留」那一步（SKILL.md 第〇之二節）同時比對本規格：

1. 這次負責人**核可**的畫面裡，有沒有本規格沒有的樣式、數值或元件？有沒有和本規格衝突、但他選了另一邊的？
2. 有的話，列成「規格升版提案」給他勾：每條寫「新樣式／出處畫面／要改哪一節／選了會怎樣／代價」。
3. 他勾了才改 `design-system.md`、`tokens.css`、`components.css`、`showcase.html`，版號 +1，並同步軟體資料庫的設計規格條目與 Codex 鏡像。
4. 沒有新樣式就一句「本次無規格升版提案」，不必出 HTML。
